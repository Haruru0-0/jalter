# Jalter

Jalter is a Discord bot with a modular design. Most features are off by default and a server admin turns them on. Replies to setup commands are private (ephemeral) and need the Manage Server permission or the bot manager role.

## Phase 1 features

- Panel: `/panel overview` shows which features are on, off or coming later (always on).
- Help: `/help` lists every feature with its commands and whether it is on; `/help feature:<name>` shows all commands of one feature (always on, anyone can use it).
- Language: English, French and Arabic, set per server (always on).
- Media: store images for the server with `/media add` and use them by name. Uploading a file straight into the storage channel does not register it; only `/media add` does.
- Embeds (always available): save named embeds with `/embed create`, edit them with the part menu (Basic info, Author, Footer, Images, Add field) or `/embed edit`, and post one with `/embed show` (in the channel you pick, default the current one). Use one in a message with `{embed:name}`.
- Post (always available): send text (`/post text`) or text with a link button (`/post buttons`) as the bot, with mentions blocked. You can only post in channels where you can see and send messages yourself.
- Greet, leave and boost messages, set with `/set greet|leave|boost ...` (channel, message, card, background, and DM for greet and boost) and tried out with `/test`. A message can hold `{embed:name}` and an optional card image.
- Auto role: give new members one or more roles, for humans, for bots, or both. The bot's highest role must sit above any role it gives, or Discord refuses.
  - `/autorole add role:<role> [target:humans|bots]` adds a role, `/autorole remove role:<role>` removes it, `/autorole show` lists the setup, `/autorole disable` turns the feature off; `/autorole add` turns it back on, even with a role already listed.
  - `/autorole timed add delay:<time> role:<role>` gives a role to a new human only after a delay, such as `30m`, `2h` or `1d` (1 minute to 30 days). `/autorole timed remove role:<role>` cancels it, including for members already waiting.
  - `/autorole reassign state:on|off` (off by default): a member who leaves gets their roles back if they return within 30 days. Blacklisted, managed and above-the-bot roles are never remembered.
  - `/autorole blacklist add|remove role:<role>` keeps a role from being given back to members who leave and return.
- Logging: 24 events in six categories (messages, members, join, server, voice, mod). Messages: delete, edit, bulk delete, invite posted. Members: role, avatar and name changes, ban, unban, timeout and timeout removed. Join and leave. Server: channels, roles, emojis, server settings. Voice: join, move, leave. Each event can be turned off with `/logging event`; message logs can skip channels, members and prefixes (`/logging ignore`, `prefix-add`). `/logging setup` creates the channels, `/logging status` shows everything, `/logging export` and `import` copy toggles and prefixes between servers. Ban, unban, timeout, channel and role creation and deletion, and some message deletes show who did it when the bot has View Audit Log; without it the log is still sent, just without the "By" field. The `mod` category receives the moderation case log (see Moderation).
- Moderation (off by default, `/moderation enable`): `/warn`, `/timeout`, `/untimeout`, `/mute`, `/unmute`, `/kick`, `/ban`, `/unban` take a `user` and a `reason`; `/timeout`, `/mute` and `/ban` also take an optional `duration` (such as `30m`, `2h`, `7d`), and `/ban` an optional `delete_days` (0 to 7). Every action gets a per-server case number and is posted to the mod log (`/logging set category:mod`). A timed ban or mute ends by itself (the bot unbans or removes the mute role and logs a case). A member who rejoins while still muted gets the mute role back. `/warnings list|edit|delete|clear|top` manages warnings (a member may list their own) and `/reason case:<n> reason:<text>` changes a case's reason, including in the mod log message. `/moderation status|reason-required|dm|timeout-default|ban-delete-days|mute-role|permitted-role-add|permitted-role-remove` are the settings (Manage Server or the bot manager role). Reasons are required by default; the member is DMed before the action; nobody can act on the owner, themselves, the bot, or anyone whose top role is at or above theirs or the bot's. The commands need the matching Discord permission (Moderate Members, Kick Members or Ban Members) or a permitted role. Run `npm run deploy` to register the new commands.
- Channel tools (part of moderation, so also off until `/moderation enable`): `/purge messages count [user] [bots] [reason]` deletes up to 100 recent messages in the current channel (never pinned ones or ones older than 14 days; the bot scans the latest 500 messages). `/purge channel [channel] [reason]` deletes a text or announcement channel and recreates it empty with the same settings, after a Confirm button (2 minutes, only the moderator who ran it can press it). It moves the logging, welcome, goodbye, boost and media channel settings to the new channel, and refuses the rules and community updates channels and a channel that holds stored media. `/slowmode seconds [channel] [reason]` (0 turns it off, max 6 hours; works in threads), `/lock [channel] [reason]` and `/unlock [channel] [reason]` (@everyone Send Messages only; unlock cannot tell its own deny from one an admin set by hand, so it clears any @everyone deny). Each action writes one line to the mod log; no cases. They need Manage Messages (purge messages), Manage Channels (purge channel, slowmode, lock, unlock) or a permitted role, and the bot needs View Channel and the same permission in the channel, plus Manage Roles for lock, unlock and purge channel, Read Message History for purge messages, and Manage Threads for slowmode in a thread (Send Messages is not required; notices are best effort). See [docs/discord-bot-setup.md](docs/discord-bot-setup.md). Run `npm run deploy` to register them.
- Auto-mod (off by default, `/automod enable`; separate from moderation): watches messages with four rules, each off until `/automod rule rule:<spam|invites|links|words> state:on`. Spam has seven checks (burst, identical, caps, emoji, mentions, attachments, link rate; turn one off with `/automod spam-check`, change its main limit with `/automod spam-limit`). Invites are checked against the server they point to (foreign invites are blocked unless allowed), links and invites have allow and block lists (`/automod domains`) and `/automod mode` to block everything except the allow list, and words has a built-in list in English, French and Arabic plus custom words (`/automod words add|remove|builtin-remove|builtin-restore|builtin|list`; a stretched spelling of a listed word like `shiiit`, accents, letter swaps such as `0` for `o`, `3` for `e`, `@` for `a` and `$` for `s`, and zero-width characters are caught). Each offence deletes the message (`/automod delete` per rule) and adds a strike; `/automod steps` sets what happens at which count (default: 3 strikes in 10 minutes gives a warn; spam also times out for 10 minutes at 5 strikes; steps like `3:warn,5:timeout:10m,8:timeout:1d`) and `/automod window` the counting window. Warn and timeout steps create moderation cases through moderation's engine; a message with no case gets one auto-mod line in the mod log. Edited messages are checked again. `/automod nickname state:on` renames members whose nickname or username holds a listed word. `/automod exempt add-role|remove-role|add-channel|remove-channel` and `/automod history [user]`, `/automod status` (shows exemptions, list modes and entries, and every spam limit). Members with Manage Server, the bot manager role, Moderate Members or a moderation permitted role, and bots, are never checked. Strikes are kept in memory and reset when the bot restarts. The bot needs Manage Messages (delete), Moderate Members (timeout) and Manage Nicknames (rename). Run `npm run deploy` to register `/automod`. Regex rules, a honeypot channel, account-age conditions, a timed role and the native Discord AutoMod trigger are not built yet.
- Reaction roles (off by default, `/reactionroles enable`): members pick their own roles from an embed message that staff post once. Setup: write the embed with `/embed create` (and `/embed edit`), then `/reactionroles create embed:<name> style:<reactions|buttons|menu>` posts it (in `channel`, default the current one; optional `type`), or `/reactionroles adopt message_id:<id> style:<style> [channel]` (channel defaults to the current one) attaches roles to an embed message the bot already posted (refused if it already has buttons or a menu). Add roles one at a time with `/reactionroles add message_id role [emoji] [label]` (reactions need an emoji; buttons and the menu need a label or an emoji) or with `/reactionroles builder message_id`, a private panel with a role picker, an Add button (it asks for the emoji and label), a remove menu and Done (only its opener can use it, for 10 minutes). `remove` takes a role off the message, `show [message_id]` lists them, `status` lists problems (a message deleted from Discord, a message with no roles, a role that was deleted, that the bot can no longer give or that has gained a staff permission, and a reactions message whose Discord message has no reactions at all) and `refresh` re-renders the message from its named embed after `/embed edit`. The style (reactions, buttons or a dropdown) is fixed per message; a message holds at most 20 roles in every style, and a custom emoji must belong to this server. `/reactionroles type` sets how it behaves: `normal` (toggle), `unique` (one role at a time), `verify` (picks only add), `drop` (picks only remove), `reversed` (reacting removes, un-reacting adds; reactions only), `binding` (one permanent choice per member, forgotten when the member leaves the server; a member who already holds one of the message's roles cannot pick another) or `lock` (nothing is given). Changing the type affects later picks only. `limit` caps how many roles one member may hold from the message (0 removes the cap), `whitelist` and `blacklist` (`mode:add|remove|clear`) choose who may use it, and `selfdestruct duration:<1h|off>` deletes the message after a delay. `purge` (after a Confirm button) removes the roles from one message, or forgets every role message in the server; it never deletes the Discord messages. `fix` re-adds the bot's own missing reactions or re-renders the buttons or menu. Roles with staff permissions, managed roles, roles at or above the bot's top role and roles you could not give yourself are refused, and every grant is checked again when a member picks: a role that has since gained a staff permission, or that the bot can no longer give, is refused and staff get one mod log line per message per hour. Deleting a role removes it from every role message and from every whitelist and blacklist. Reactions made while the bot was offline are not replayed, and `fix` only re-adds the bot's own reactions: it never gives or takes roles, so roles can drift after downtime (buttons and menus are not affected). Needs Manage Roles, and for reactions Add Reactions, Read Message History and Manage Messages (whatever the type, the bot removes members' reactions, for example on a refused pick or a `unique` swap); changing the type of a reactions message checks these again. Run `npm run deploy` to register `/reactionroles`; migration 009 runs on the next start.
- Autoresponder (off by default, `/autoresponder enable`; stages 1 to 3 of 3): replies to messages that match a trigger. A rule is a trigger, a match mode and a short script. `/autoresponder add [match]` and `/autoresponder edit id` open a form for the trigger and the script. Match modes: `exact` (the whole message, ignoring case and outer spaces), `startswith`, `endswith`, `includes` and `regex` (the trigger is a regular expression; patterns the matcher cannot run safely are refused when you save; messages over 1000 characters never match a regex rule). A trigger of a non-regex mode holds up to 100 characters and a server up to 100 rules. When several rules match, one answers: any non-regex rule before a regex rule, then the longest trigger, then the lowest id. If that rule cannot run (a gate fails or its cooldown is active) no other rule is tried. `editmatchmode`, `toggle` (one rule on or off), `remove`, `list` and `show` manage the rules. `/autoresponder test message:<text>` is a dry run: it shows which rule would answer and what it would say, and sends, deletes, grants and changes nothing. Bots, webhooks, DMs and a message that auto-mod already deleted or punished are never answered.
  A script is plain text with `{function}` and `{function:arg|arg}` calls; `\{`, `\[`, `\|` and `\` write the symbol itself. Everything that is not a function call is the reply, and an unclosed `{` is an error when you save. Functions (script limit 4000 characters; mistakes are listed when you save and nothing is stored): gates `{cooldown:seconds}` (1 to 604800, per member and rule), `{requirerole:role|...}`, `{denyrole:...}`, `{requireperm:Permission|...}`, `{denyperm:...}`, `{requirechannel:channel|...}`, `{denychannel:...}`, `{requireuser:user|...}` (up to 10 arguments each; a member passes a require gate with any one of them); actions `{addrole:role}`, `{removerole:role}` and `{setnick:text}` (3 role or nickname changes in total), `{react:emoji}` on the message and `{reactreply:emoji}` on the reply (5 reactions in total, `{react}` and `{reactreply}` counted together), `{delete}` removes the trigger message; reply options `{embed}`, `{embed:#RRGGBB}` or `{embed:name}` (a stored embed from `/embed create`), `{sendto:channel}`, `{dm}`, `{silent}` and `{delete_reply:seconds}` (1 to 300). Each of `cooldown`, `embed`, `sendto`, `dm`, `delete`, `silent` and `delete_reply` may appear once. The reply uses the usual placeholders (`{user}`, `{user_name}`, `{server_name}`, `{server_membercount}`, `{date}`, `{newline}` and the rest of the greet list) plus `{user_id}`, `{user_nick}`, `{user_joindate}`, `{user_createdate}`, `{user_displaycolor}`, `{user_boostsince}`, `{server_id}`, `{server_boostlevel}`, `{channel}`, `{channel_name}`, `{message_id}`, `{message_content}` and `{message_link}`. Replies never ping roles, `@everyone` or `@here`; they ping only the sender through `{user}`, the owner through `{server_owner}` and the users mentioned in the script itself, never a mention that comes from what the member wrote (`{message_content}`, a name).
  Worked example, a rule with trigger `!rules` and match `startswith`: `{requirerole:Member}{cooldown:60}{embed:rules}{delete_reply:30}{react:👍}` answers members only, once a minute each, with the stored `rules` embed that disappears after 30 seconds. Another, trigger `i am new`, match `includes`: `Welcome {user}, you are member number {server_membercount_ordinal}!{addrole:Newcomer}`. Role changes are checked twice: when you save (the role must exist, must not hold a staff permission, must be below the bot and below you, and must not be managed) and again each time the rule runs. A failed `requirerole` gate answers with a short notice that deletes itself after 8 seconds, and a cooldown that is still running does the same with the seconds left (not when the script has `{silent}`); each is shown at most once per 30 seconds per member and rule. When a rule fails while running (a role the bot can no longer give, a missing permission) staff get one mod-log line per rule per hour. Pending `{delete_reply}` deletions are lost when the bot restarts. Stages 2 and 3 are described below. The bot needs Send Messages, Manage Roles (role changes), Manage Messages (`{delete}`), Add Reactions (`{react}`, `{reactreply}`) and Manage Nicknames (`{setnick}`). Run `npm run deploy` to register `/autoresponder`; migration 010 runs on the next start.
  `/autoresponder builder` opens a private panel (managers only) that builds a new rule with menus and buttons instead of a script. It only creates new rules; `edit` still opens the script form. Pages, picked from a menu at the top: Basics (trigger and match mode), Reply (reply text, where it goes: same channel, direct message or another channel, delete the trigger message, silent, an embed that is a saved embed or a plain colour, delete the reply after 1 to 300 seconds), Conditions (cooldown, needs or is blocked by a role, needs or is blocked by a permission, only or not in channels, only for members; up to 25) and Actions (give or remove a role, change the nickname, react to the message or to the reply), Random (stage 2, see below), Buttons (stage 3, see below), then Review with Save and Cancel. Every change is turned into a script and compiled at once, so the usual limits and role safety checks apply and a refused change is explained and not applied. The reply text is kept as typed, so placeholders such as `{user}` work. A `}` is refused in the cooldown seconds, the permission name, the nickname, the emoji, the colour and the delete-reply seconds, because the script format has no way to write it inside a function; a typed permission name containing `|` is refused too. A destination of another channel needs a channel picked before Save or Try it. Conditions accept any role (they only test membership); actions refuse roles with a staff permission, managed roles and roles at or above the bot or you. `Try it` asks for a sample message and shows what the rule would do: it sends, deletes, grants and changes nothing. `Edit script text` opens the generated script for hand editing; this is one way, the panel then only offers Basics and Review and cannot go back to the menus. The draft lives in memory only until Save: a panel expires after 15 minutes without a click, each member has one panel per server (opening another replaces it), and a bot restart loses every draft. Only the member who opened the panel can use it. Run `npm run deploy` once so the new subcommand is registered.
  **Stage 2: random values and the member's words** (no new command, so no `npm run deploy` is needed; no migration; no new permission). Rules saved before stage 2 keep working unchanged and stay on the old compiled format until you edit them. Random functions (each is checked when you save; at most 4 `range`, 4 `choose`/`weightedchoose` and 4 `lockedchoose` per script, 25 options at most in one choice):
  - `{choose:a|b|c}` picks one option; read it as `[choice]`. 8ball, trigger `!8ball`, match `startswith`: `{choose:Yes.|No.|Maybe.}The ball says: [choice]`. A second choice is `[choice2]` (up to `[choice4]`). Options and locked values can hold the member's words: `{choose:Hi [$1]!|Hey [$1]!}[choice]` replies `Hi Sam!` or `Hey Sam!` to `!greet Sam` (`\[$1]` in an option stays literal).
  - `{range:min-max}` draws a whole number, both ends included; read it as `[range]` (`[range2]`... for more). Trigger `!roll`, match `exact`: `{range:1-6}You rolled a [range].` Negative ends work (`{range:-5-10}`); each end is at most 1000000000 and the first must not be above the second.
  - `{weightedchoose:80%|15%|5%}` picks by weight (integers or decimals, relative, they need not add up to 100, not all zero); `[choice]` is then the position of the pick (1, 2 or 3). `{lockedchoose:Common find|Rare find|Legendary find}` gives the value paired with the pick of the choice of the same number (the nth `lockedchoose` goes with the nth `choose` or `weightedchoose`); read it as `[lockedchoice]`. The counts must match. A weighted reply: `{weightedchoose:80%|15%|5%}{lockedchoose:Common find|Rare find|Legendary find}You got: [lockedchoice]`.
  - Each random value is drawn once per message, so the reply text, the nickname and the actions all see the same result.
  The member's words: for `startswith` and `includes` rules the words after the trigger (for `includes`, after its first occurrence) are `[$1]`, `[$2]`... up to `[$20]`; `[$2+]` is word 2 and everything after it with the spacing kept; `[$2-3]` is words 2 to 3. A missing word is empty. Only `exact`, `endswith` and `regex` rules have no words: `[$1]` renders empty there (the save reply warns) and `{requirearg}` is refused. Words come from the original message, found with the same case folding as the match, so `!SAY hello` works for a `!say` trigger. `!say` with `startswith`: `{requirearg:1}[$1+]` (a member who types only `!say` gets one short notice: "Missing or invalid word 1 after the command (expected: a word).").
  `{requirearg:N}` requires word N to exist; `{requirearg:N|type}` also checks its type: `user` (a mention or id of a current member), `channel`, `role` (mention or id of an existing one), `color` (`#rrggbb`) or `number` (optional `-`, digits, optional decimals). When a check fails the rule does not run and the member gets that one notice, deleted after 8 seconds, shown at most once per 30 seconds per member and rule, and not with `{silent}`; it is checked before the cooldown starts. A second `{requirearg}` for the same N is refused (`DUPLICATE_FUNCTION`). A word checked as `user` is written as a mention in the reply, even when the member typed a bare id; in a `{setnick}` (also through a `{choose}` or `{lockedchoose}` option) it is the member's display name instead. `!hug`, `startswith`: `{requirearg:1|user}{user} hugs [$1]`.
  Brackets: only the exact forms `[$N]`, `[$N+]`, `[$N-M]`, `[range]`, `[choice]`, `[lockedchoice]` (and the numbered `[range2]`... `[lockedchoice4]`) are special; any other `[Note]` stays plain text and `\[` always writes a bracket. `[range]`, `[choice]` and `[lockedchoice]` are plain text unless the script has the function that makes them. A `}` still cannot be written inside a function argument.
  Pings: a person named in the reply pings only when the script checked that word as `user` (`{requirearg:N|user}`); any other mention a member types in a word, and any mention inside a `{choose}` or `{lockedchoose}` option (written by the script writer, or a checked user word placed in an option), is shown but does not ping; never roles or everyone.
  Role targets: `{addrole:Role|[$1]}` and `{removerole:Role|[$1]}` change another member's role. The target must be a word checked with `{requirearg:N|user}`, and the script must also contain a `{requirerole}` or `{requireperm}` (saving is refused otherwise; the check is only that one exists, so choose a meaningful gate). `!role`, `startswith`: `{requirearg:1|user}{requirerole:Mods}{addrole:Red|[$1]}Gave the role to [$1]`. A target counts toward the 3 role/nickname actions. When the rule runs the target must still be in the server and one the bot can manage (not the owner, not the bot, not above the bot), and the role (for `addrole` and for a targeted `removerole`) must still be one the bot may give (no staff permission, below the bot); otherwise that change is skipped, the rest of the script runs and staff get the usual run-error line. `editmatchmode` recompiles the script under the new mode and refuses the change only when the new mode has no words for a `{requirearg}` (`NO_ARGUMENTS_IN_MODE`, for example a `{requirearg}` rule moved to `exact`); other problems in the stored script (a role above the member running it, a deleted role, embed or channel) do not block a mode change, and a `[$1]` in a mode without words only adds the warning.
  `/autoresponder test` and the builder's Try it use the same code as a live message: they take the words from the sample, resolve users against the server, draw random values and list "Random values drawn" and "Would ping"; nothing is sent. The builder's Save and Try it show the same warnings as the script form (for example that `[$1]` is empty in an `exact` rule). In the builder, the Random page adds and removes random values (range, choice, weighted choice, locked choice) and lists the tokens to type in the reply text; the Conditions page can add "Needs a word after the trigger" (any word, a member, channel, color, role or number); a role action can target the member in word N instead of the sender.
  **Stage 3: buttons on replies.** A reply can carry buttons. A button is a stored thing you create once and attach to any number of rules; pressing it runs its own small script. Run `npm run deploy` once to register the new `button` subcommand group; migration 011 runs on the next start; no new permission.
  - Stored buttons (managers only, like the other setup commands): `/autoresponder button add name:<name>` takes a name (a-z, 0-9, `_` and `-`, 1 to 16 characters), a `style` (blue, the default, green, grey or red), `invoker_only` (default off) and `limitations` (`none`, the default, `limited` or `strict`), then opens a form for the label (1 to 80 characters), an optional emoji and the button's script (up to 4000 characters). `button edit` opens the same form filled in (the options default to the stored values), `button remove` deletes one and `button list` shows every button with its colour, limitation and invoker setting. A server holds up to 50 buttons; a duplicate name is refused. The button's script is compiled when you save, with the same functions and limits as a rule script; there is no match mode, so `[range]`, `[choice]` and the other random tokens are always live, and the member's words `[$1]`... are the words of the message that posted the buttons. Each add, edit and remove writes one line to the mod log.
  - Attaching: `{addbutton:name}` puts a stored button on the reply and `{addlinkbutton:label|url}` or `{addlinkbutton:label|url|emoji}` adds a link button (http or https, at most 512 characters, label 1 to 80 characters). Buttons appear in script order, up to 25 per reply, five to a row. They are checked when you save: an unknown name (`BUTTON_NOT_FOUND`), a bad name, a bad link, a 26th button, `{dm}` in the same script (buttons need a message in a channel; `{sendto:#channel}` is fine and the buttons go on the message sent there) and a reply with buttons but no text and no named embed (`BUTTONS_NEED_TEXT`; a plain `{embed}` uses the text as its description, so it does not count on its own) are each refused and nothing is saved. Attaching a stored button whose script gives or removes a role is checked against you as if you had typed that role yourself: if the role is above your highest role it is refused with `ROLE_ABOVE_YOU` (a staff role or one above the bot is refused too), so a lower manager cannot reuse an admin's role button. The check covers the whole chain: the buttons that button attaches are checked too, and so on, and a chain of more than 25 buttons is refused (`BUTTON_CHAIN_TOO_LONG`). It runs when you save, and rules and chains hold buttons by name and read them fresh when a button is pressed, so a button edited after the rule was saved, or removed and created again under the same name, is not re-checked; a rule naming a removed button picks up whatever button later takes that name (`button remove` does not touch rules). The server owner is not limited. At run time the button's label, emoji and colour are read fresh, so editing a stored button changes how it looks on the next reply. A button that was removed after the rule was saved is left out and staff get the usual run-error line (`BUTTON_MISSING`); the rest of the reply goes out.
  - Worked examples (create the buttons first with `/autoresponder button add`). A "Show rules" button: name `rules`, label `Show rules`, script `Rule 1: be kind. Rule 2: no spam.`; a rule with trigger `!help` (`exact`) and the script `Need the rules? {addbutton:rules}` posts the question with the button and anyone who presses it gets the rules as a public reply. An asker-only confirmation: name `confirm`, label `Yes`, `invoker_only:true`, `limitations:limited`, script `{user} confirmed.`; rule `Are you sure, {user}? {addbutton:confirm}`: only the member who triggered the message can press it, once. A one-press claim: name `claim`, `limitations:limited`, script `{user} claimed the prize!`; rule `The first to press wins! {addbutton:claim}`: the first press runs the script and the button is disabled for everyone. A link: `Read more {addlinkbutton:Docs|https://example.com/docs|📖}`. A button's script can attach more buttons (`More help: {addbutton:rules}`): the new reply belongs to the member who pressed, and the original words and random results carry on, so `[$1]` and `{requirearg}` keep working at every step. The words after the trigger are stored with the message whenever the reply carries buttons, even when the rule's own script reads none (`Noted {addbutton:answer}` on a `startswith` rule still gives the `answer` button its `[$1]`).
  - Limitations (per posted message): `none` never changes anything and can be pressed again and again (it is only refused once the message is locked); `limited` lets that one button be used once and disables it afterwards; `strict` locks the whole message, so after one press every button on it, including `none` ones, is refused and shown disabled (link buttons are never disabled). Two members pressing at the same moment are decided by the database: one wins, the other gets "already used" or "closed". `invoker_only` restricts the button to the member whose message made the reply (or, for a chained reply, the member who pressed the earlier button).
  - What a press does, in order: it is acknowledged at once; the feature must be on; the posted message must still be stored and not expired; the rule that posted it must still exist and be enabled; the stored button must still exist; a press floor of one press per member per message every 3 seconds (it starts on every press that gets this far, so a press refused by a condition below still starts the presser's 3 seconds), then `invoker_only`; the button script's gates (`requirerole`, `requirearg` and so on) and word checks (a restored word is checked again, so a user who has left fails); only then the `limited`/`strict` claim, so a member who fails a condition never uses up a one-press button or locks the message; then the button's `{cooldown}` (per member and per button of that posted message); then the script runs: role changes, nickname and reactions apply to the member who pressed, and the reply is posted publicly as a reply to the button's message. Every refusal ("expired", "only the member who triggered this", "already used", "closed", "slow down", "you cannot use this button", the word notice, the cooldown with its seconds) is a private message only the presser sees. The rule's own conditions and its rule-level cooldown are not used for presses. A `{delete}` in a button script deletes the message that carries the buttons. Pings follow stage 2: only words checked as a user can ping, and restored words are re-checked at press time.
  - Lifetime: a posted button works for 14 days; after that a press answers "expired" and housekeeping deletes the stored record (a bot restart changes nothing: the state is in the database). Disabling a rule (`/autoresponder toggle` or `disable` for the whole feature) stops its posted buttons, which then answer "expired"; editing a rule changes nothing. Removing a stored button leaves the messages that carry it in place; pressing it answers "expired", and a rule that still names it skips it when it replies. Role handout buttons stay with reaction roles (`/reactionroles`); autoresponder buttons run scripts.
  - Builder: a Buttons page (between Random and Review) lists the saved buttons (the first 24) in a menu to add one, has an "Add link button" form and a menu to remove an added button; the summary shows them and Try it and Save compile the result like any other change.
- Bot manager role: `/panel manager-role` lets a role use the setup commands. Only members with Manage Server can set or clear it, and @everyone or bot-managed roles are refused.
- Info: `/userinfo`, `/avatar`, `/banner`, `/serverinfo`.

## Prerequisites

- Node.js 22 or newer
- Docker Desktop (runs Postgres)

## Setup

1. Copy `.env.example` to `.env` and fill it in:
   - `DISCORD_TOKEN`: the bot token from the developer portal.
   - `CLIENT_ID`: the application ID.
   - `DEV_GUILD_ID` (optional): a test server ID. When set, commands register to that server only and update instantly.
   - `DATABASE_URL`: defaults to the Postgres from `docker-compose.yml`.
2. Run:

```
docker compose up -d
npm install
npm run deploy
npm start
```

`npm run deploy` prints `Registered N commands ...` and `npm start` prints `Logged in as <bot>`.

Postgres only listens on this computer (`127.0.0.1`). Before hosting the bot anywhere reachable from the network, change the database password (`POSTGRES_PASSWORD` in `docker-compose.yml` and the password in `DATABASE_URL`) from the default `bot`.

## Discord developer portal

Step-by-step with troubleshooting: [docs/discord-bot-setup.md](docs/discord-bot-setup.md). The short version:

1. Go to the Discord developer portal and create an application.
2. Open the Bot tab, create the bot and copy its token into `.env`.
3. Under Privileged Gateway Intents enable Server Members and Message Content. The bot also uses the Guilds, Guild Messages, Guild Expressions (emoji events), Guild Moderation (ban and unban events) and Guild Voice States (voice events) intents, the last three used by logging, and Guild Message Reactions (reaction roles); those are not privileged, so they are granted automatically and need no switch in the portal.
4. Copy the application ID into `.env` as `CLIENT_ID`.
5. Invite the bot with the `bot` and `applications.commands` scopes and these permissions: View Channels, Send Messages, Read Message History, Embed Links, Attach Files, Manage Roles, Add Reactions, Manage Messages, Manage Channels, Manage Nicknames, Kick Members, Ban Members, Moderate Members. Read Message History lets the bot fetch stored images from the media channel and read reaction role messages. Reaction roles use Manage Roles, Add Reactions, Read Message History and Manage Messages (the bot adds its own reactions and removes members' reactions). Add View Audit Log if you want logs to show who banned, timed out or deleted something, Manage Messages is for `/purge messages` and for auto-mod deleting messages, Manage Nicknames is for the auto-mod nickname check and the autoresponder's `{setnick}`. The autoresponder also uses Send Messages, Manage Roles, Manage Messages and Add Reactions. Manage Channels is needed for `/purge channel`, `/slowmode`, `/lock` and `/unlock`, and lets the bot create channels itself: `/logging setup`, and the log, welcome, goodbye and boost channels it makes when you did not choose one (a channel you choose is always used as is; nothing is created then).

## Manual check on a test server

A tick-box checklist for every feature is in [docs/testing-checklist.md](docs/testing-checklist.md). The numbered list below is the original short version.

Run these on a test server with the bot invited and started. Confirm each item.

1. `/panel overview` shows Panel and Language as Core, other Phase 1 features Off, later phases Coming soon.
2. As a normal member (no Manage Server), every setup command is refused with the permission message.
3. `/language set` to French changes `/panel overview` to French; Arabic shows Arabic.
4. `/media setup`, `/media add logo`, `/media list`.
5. `/embed create name:rules` works without enabling anything and opens the editor; use the menu to set the title, description and fields, then `/embed edit title ...` and `/embed show`. An embed with `logo` as its image shows the image.
6. A text over the limits (for example a 300-character title) shows the error and saves nothing.
7. `/post` works without enabling anything; `@everyone` in the text does not ping.
8. `/set greet channel`, then `/set greet message` with text, and again without text (it opens the form). Put placeholders such as `{user}` and `{server_name}` in it, add `{embed:rules}`, and run `/test greet`. Then `/set greet message none` turns that one message off (`/test greet` says it is off) while the leave and boost messages keep working.
9. `/set greet card on` and `/test greet`: the card looks right with an Arabic username. Try `/set greet background logo` and `/set greet dm on` (the DM arrives).
10. Repeat step 8 for `/set leave ...` and `/set boost ...` with `/test leave` and `/test boost`, and the card and DM checks of step 9 for boost. Leave has the card and background but no `dm` option.
11. `/autorole add role:<role>` for humans and `/autorole add role:<role> target:bots` with another role, then `/autorole show`: both are listed. A new human account gets the first role and a bot gets the second.
12. `/autorole timed add delay:1m role:<role>`, then add a new account: it gets the role after about a minute.
13. `/autorole timed add delay:1d role:<role>`, add a new account, then `/autorole timed remove role:<role>` with that role: the waiting member never gets it.
14. `/autorole reassign state:on`, give a member a role, let them leave and rejoin: the roles come back. With `state:off` they do not.
15. With `reassign` on, give a member a role, then `/autorole blacklist add` that role. Have the member leave and rejoin: they do not get the role back. `blacklist remove` allows it again.
16. `/logging set messages`: edit and delete a message and see the log; edits inside the log channel itself are not logged.
    a. `/logging event event:messageEdit enabled:false`, edit a message: nothing is logged. `enabled:true` brings it back. `/logging status` lists the disabled events.
    b. `/logging ignore channel:<channel>`, `/logging ignore member:<member>` and `/logging prefix-add prefix:!`: deleting or editing a message in that channel, by that member, or starting with `!`, is not logged. `unignore` and `prefix-remove` undo each.
    c. `/logging set voice` then join, switch and leave a voice channel: three logs. Muting or deafening yourself logs nothing.
    d. With View Audit Log granted, ban a test member, then unban and time out: each log has a "By" field with you. Remove View Audit Log from the bot and repeat: the logs still arrive without "By".
    e. `/logging setup` creates a private "Logs" category with log-messages, log-members, log-joins, log-server and log-voice and points the categories at them. Running it again creates a second new "Logs" category and channels and leaves the old ones in place; delete them yourself if unwanted.
    f. `/logging export`, then on another test server `/logging import code:<code>`: event toggles and prefixes are copied (channels and ignored members are not). `/logging import code:garbage` shows an error and changes nothing.
17. `/info enable`, then `/userinfo`, `/avatar`, `/banner`, `/serverinfo` work; with `/info disable` they refuse.
18. Delete the greet channel, run `/test greet`: the bot does not crash.
19. `/help` lists the features with On/Off and their commands; `/help feature:autorole` lists every autorole command; `/help feature:nonsense` says there is no such feature.
20. Stop and restart the bot, then run `docker compose restart`: all settings are still there.
21. Moderation: see section 11 of the checklist. In short: `/moderation enable`, `/moderation mute-role role:<role> apply:true`, then `/warn`, `/timeout`, `/mute duration:1m`, `/ban duration:1m` and `/unban` on a spare account, then `/reason` and `/warnings list`. Each action gets a case number and a post in the mod log. Channel tools (`/purge`, `/slowmode`, `/lock`, `/unlock`) are in section 11 too.
