# Decisions

Record choices that are not obvious from the code, with the reason.

- 2026-10-14: Memory is an Obsidian vault in `docs/memory/`; code structure comes from Graphify (`graphify-out/`, git-ignored, refresh with `graphify update .`).
- 2026-10-14: A global Stop/SessionStart hook (`~/.claude/hooks/memory-sync.mjs`) asks before setting up memory in a new git project and before updating notes; Graphify map refreshes automatically. Declined projects are listed in `~/.claude/memory-sync-declined.json`.
- Features are modular and off by default; admins opt in per server. Why: keeps the bot quiet and permissions minimal until needed.
- Setup replies are ephemeral and gated by Manage Server or the bot manager role (`core/guard.js`).
- All user-facing text lives in the three i18n files, so nothing is hard-coded in English.
- Autorole: timed roles and sticky memory (`reassign`, 30 days) live in autorole, not a separate "stickyroles" feature. Blacklisted, managed and above-the-bot roles are never remembered.
- Postgres binds to `127.0.0.1` only; change the default password `bot` before hosting anywhere reachable.
- Tests run with `--test-concurrency=1` because they share the database.
- Scheduler (built 2026-10-14, [[architecture]]): jobs are at-least-once. A tick claims due rows (`FOR UPDATE SKIP LOCKED`), the attempt is counted at claim, and the claim expires after 5 minutes (`CLAIM_MS`), so a job whose process died is re-run later. A handler that returns finishes the job (row deleted, including "nothing to do"); one that throws is retried. Max 5 attempts (`MAX_ATTEMPTS`); backoff after attempts 1-4 is 1, 5, 15 and 60 minutes, then the job is dropped with a `console.warn`. Job types with no registered handler are never claimed or counted and wait untouched (one warning per type per process). Scheduling the same guild+type+key twice keeps one row with the new due time and resets attempts; this needs a non-null key (NULL keys never conflict, so keyless jobs always add a row), and `cancelJobs` with no key matches any key. Finishing a job (`completeJob`/`failJob`) also matches the claimed attempts, so a handler still running when its key is rescheduled cannot delete or move the new row. Spec: `docs/tiered-powers/specs/2026-10-14-scheduler-design.md`.
- Auto role timed grants: the handler finishes without granting when the feature is off or the role is no longer in the timed list; unknown member/role and other HTTP 4xx (except 429) log and finish; network, 5xx and 429 errors throw and retry.
- Moderation (built 2026-10-14, spec `docs/tiered-powers/specs/2026-10-14-moderation-design.md`, see [[architecture]]): a case and its number are created only after the Discord action succeeds, so refusals and Discord failures use no number. Order is: checks, DM (best effort), Discord action, case, schedule, mod log. Hidden `modAction` event because `/logging event` already has 25 choices (the Discord limit). Permitted roles (max 10) let holders use every moderation command without the Discord permission, but never the settings, and they do not bypass required reasons or the hierarchy rules. Commands have no default member permission (so permitted-role holders can see them); the check is in code (`canUseAction`: ModerateMembers for warn/timeout/mute/reason/warnings, KickMembers for kick, BanMembers for ban/unban). Nobody can act on the owner, themselves, the bot, or a member at or above their own (owner exempt) or the bot's top role. Warnings `edit`, `delete` and `clear` mutate warn cases (inactive, not erased) and post nothing to the mod log. Timed ends record a case by the bot with the reason "expired" and run even if the feature was switched off.
- Channel tools (built 2026-10-15, spec `docs/tiered-powers/specs/2026-10-15-channel-tools-design.md`, see [[architecture]]): they live inside the moderation feature and create no cases (not punishments); each action writes one mod log line. Permissions reuse `canUseAction` (a permitted role may use them all, including `/purge channel`). `/purge channel` clones and deletes instead of removing messages one by one; the order is clone, set position, move saved channel ids in one transaction, delete the old channel, so a failure before the delete leaves the original untouched (the clone is removed again) and the moderator is told. Confirm is a button valid 2 minutes, only the runner can press it, and a per-channel in-progress guard stops double runs; access is re-checked on Confirm. Lock and unlock touch only the @everyone Send Messages overwrite.
- Auto-mod (planned 2026-10-16, see [[roadmap]]): own feature key `automod` with its own enable (not under `/moderation enable`), reusing moderation `runAction`; strikes kept in memory (reset on restart), history in a table; regex through the `re2` package (linear-time, Node `^22.22.2 || ^24.15.0 || >=26.0.0`); a case already logs itself, so the auto-mod line is posted only when no case was made.
- Auto-mod pipeline (built 2026-10-16, see [[architecture]]): one enforcement per message. When several rules cross a step on the same message, only the most severe step runs (a timeout beats a warn, then the longer timeout), and each rule that crossed its top step resets its strikes (the reset runs before the delete and the action are awaited, so a strike added meanwhile is kept). Only spam escalates by default (`3:warn,5:timeout:10m`); the other rules default to `3:warn`. The first-message nickname check and the rename cooldown are keyed by guild and user. Invite lookup has three outcomes: a guild id, `null` (unknown invite, error 10006, cached 10 minutes) and `undefined` (lookup failed or timed out after 3 s, not cached, the code is skipped, fail open). Bad words match whole tokens exactly first; a stretched spelling (`fuuuck`) matches only through a second, squeezed comparison used when the text has a repeated letter, so `as` does not match `ass`. A refused action (missing permission, hierarchy) is only logged to the console; the message is still deleted and the auto-mod line and history row are still written.
- Auto-mod Phase 2 (built 2026-10-17, see [[architecture]]): regex goes through `re2` (linear time, so a hostile pattern cannot hang the bot), max 10 patterns of 250 characters, matched case-insensitively against the first 1000 raw characters, not normalised text. Age limits are checked per rule before its detector runs. The timed role is scheduled first and the role added second (a failed add cancels the job); a member already holding the role is skipped unless our own removal job is pending, in which case the removal time moves. The honeypot rule is enforced alone, after the exemption check, with a one-strike timeout default. The native rule shares the strike store with message rules and dedupes executions for 5 s on `ruleId:userId:messageId`, or `ruleId:userId:c:<content>` when Discord blocked the message (no message id).
- Verification design (2026-10-17): the gate is a Verified role (fails closed if the bot is down) rather than an Unverified role handed out on join. Existing members get Verified before any channel is hidden. Only channels `@everyone` can view are changed, so Verified never opens a private channel. Undo keeps the first (pre-setup) overwrite bits per channel. Gif reactions went to Phase 5; the Klipy API needs written approval for server-side bot use, nekos.best needs no key. See `docs/tiered-powers/specs/2026-10-17-verification-design.md`.
- Verification captcha (2026-10-17): always English whatever the server language (image uses Latin letters and digits only; captcha messages are fixed English). The image reuses the existing `@napi-rs/canvas` and Noto fonts, so no new dependency. Plan: `docs/tiered-powers/plans/2026-10-17-verification.md`.
- Verification rollout (built 2026-10-17, see [[architecture]]): grant and gate are two scheduler jobs, and the gate only runs once `grantDone` is set, so no member is locked out while the grant is unfinished. Every step is repeatable and the final state change is a single conditional UPDATE. On the last scheduler attempt an error ends the rollout as `failed` (logged) rather than leaving `rolling_out` with no job. Setup captcha mode is selectable at setup and later via `/verification mode`.
- Verification final review fixes (2026-10-18, see [[gotchas]]): gate and revert read a forced fetch of the channel (the discord.js overwrite cache lags our own writes); every channel is gated on its own, synced or not; a channel created inside a gated category takes the category's recorded original as its own (chosen over fixing it in `remove`, so the record is right from the start and a later list change also works); the Verified role must not carry staff permissions (setup and every grant) and a role the admin picks must be below them; `failed` counts as running for new channels and bots; `remove` turns the feature off before restoring and the gate job undoes a channel it gated after that.
- Verification re-review minors (2026-10-19, see [[gotchas]]): setup and Confirm refuse while undo records exist (restart-safe, chosen over an in-memory lock alone; the shared in-flight guard already covers a remove running in the same process). A staff Verified role is shown by `/verification status` and logged once per guild per hour (in-memory throttle). The overwrite write still merges onto the discord.js cache after the forced fetch; a cache-free write was not adopted (see the residual in [[gotchas]]).
