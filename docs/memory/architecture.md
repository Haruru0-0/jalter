# Architecture

Discord bot: discord.js 14, Node 22+, ESM, Postgres in Docker. Entry `src/index.js`; slash commands registered by `src/deploy-commands.js`.

## Layout
- `src/features/<name>/index.js` - one folder per feature; each is listed in `src/modules.js` (the loader's module list).
- `src/core/` - shared helpers: `guard.js`, `registry.js`, `toggle.js`, `permissions.js`, `replies.js`, `placeholders.js`, `mentions.js`, `send.js`, `lists.js`, `members.js`, `loader.js`, `scheduler.js`, `duration.js` (`parseDuration`, `formatDuration`; moved out of autorole).
- `src/db/` - `index.js` (pool, `resetDb()` for tests), `settings.js`, `migrations/` (001_init, 002_named_embeds, 003_autorole_tables, 004_scheduled_jobs, 005_autorole_to_scheduler, 006_mod_cases, 007_automod_history).
- `src/i18n/` - `en.json`, `fr.json`, `ar.json`, and `index.js` with `t(lang, key, vars)` and `getLang`.

## Key pieces
- **Registry** (`core/registry.js`): `FEATURES` lists every feature with phase, command and enable command. Optional fields: `commands` (several top-level commands, e.g. `set` + `test`), `byKey` (a shared command like `/set` whose subcommands are split per feature key), `alwaysOn`. Phase 2-5 entries are "coming soon" stubs with `command: null`. `alwaysOn` features skip the enabled check.
- **Guard** (`core/guard.js`): `guard(interaction, ctx, key, {requireManager, requireEnabled})` checks guild-only, manager permission, and enabled state, replies ephemerally on failure, and returns the guild language on success. Almost every command handler starts with it.
- **Settings** (`db/settings.js`): `guild_settings(guild_id, feature, enabled, config jsonb)`. `getFeature` returns `{enabled:false, config:{}}` when no row; `setFeature` upserts and merges config.
- **Toggle** (`core/toggle.js`): shared `enable`/`disable` subcommands.
- **Scheduler** (`core/scheduler.js`, table `scheduled_jobs`: id, guild_id, type, key, payload jsonb, due_at, attempts, claimed_until; unique on guild_id+type+key): one shared, restart-safe job runner. Helpers `scheduleJob` (same guild+type+key updates the row, resets attempts; this needs a non-null key, since NULL keys never conflict and always insert a new row), `cancelJobs` (by guild, type, optional key, optional payload containment; with no key it matches any key), `claimDue`, `completeJob`, `failJob`. `startScheduler(ctx, registry)` ticks every 30 000 ms (timer is unref'd, a tick never overlaps the previous one) and `index.js` starts it inside the `ClientReady` handler, so nothing runs before the client is ready. Each tick runs every feature's `housekeeping` functions, then claims due jobs of registered types and runs their handlers. A feature adds job types by exporting `jobs` (`{ 'type': async (ctx, job) => ... }`) and per-tick functions by exporting `housekeeping` (`async (ctx, { now }) => ...`); `collectModules` in `loader.js` gathers both and throws on a duplicate job type. Handler contract and retry rules: see [[decisions]] and [[gotchas]]. Auto role is the first user: job type `autorole.grant`, handler `grantTimedRole`, housekeeping `purgeRememberedRoles` (sticky-role memory cleanup).
- **Moderation** (`features/moderation/`): `store.js` (tables `mod_cases` and `mod_counters`, migration 006; `createCase` takes the next per-guild number and inserts in one SQL statement; also warnings list/edit/deactivate/clear/top, `getCase`, `setCaseReason`, `setCaseLog`, `isCurrentlyMuted`), `config.js` (`readConfig` defaults, permitted roles), `rules.js` (`canUseAction`, `checkTarget` hierarchy, `checkDuration`), `actions.js` (`runAction` engine, job handlers `expireBan`/`expireMute`, `reapplyMute` on `GuildMemberAdd`), `format.js` (mod log embed and DM text), `commands-actions.js`, `commands-warnings.js`, `index.js` (the `/moderation` settings command; exports `commands`, `events`, `jobs`). `runAction` returns `{ok:true, modCase, warnings}` or `{ok:false, reason}`; `warnings` may hold `dm_failed`, `case_not_saved`, `log_failed`, `schedule_failed`. Timed actions are scheduler jobs `mod.unban` and `mod.unmute` (key = user id, payload `{userId}`).
- **Channel tools** (`features/moderation/`): `tools-common.js` (`checkToolAccess` checks `canUseAction`, channel type, that the member can view the channel, and that the bot holds ViewChannel plus the action permission and extras; `postNotice`; `logTool` writes one `modAction` line and never throws), `channel-move.js` (`moveChannelId` rewrites a channel id in the `logging`, `greet`, `leave`, `boost` and `media` settings rows inside one transaction with `FOR UPDATE`; `mediaHoldsChannel`), `commands-channel.js` (`/slowmode`, `/lock`, `/unlock`), `commands-purge.js` (`/purge messages|channel`, pure `selectPurgeTargets`, button handler with prefix `purge`). `ACTION_PERMISSIONS` in `rules.js` gained `purge` (ManageMessages) and `purgeall`, `slowmode`, `lock`, `unlock` (ManageChannels). They create no cases. See [[features-built]].
- **Mod log**: `sendLog` (logging) now returns `{channelId, messageId}` where it posted, or `null`. Moderation posts through the hidden event `modAction` (`HIDDEN_EVENTS` in `logging/events.js`, `categoryOf` maps it to the `mod` category), which is not in `EVENTS`, so it is not a `/logging event` choice. The returned ids are stored on the case so `/reason` can edit the message.
- **Auto-mod** (`features/automod/`): `config.js` (`readConfig` defaults and list/step mutators), `normalize.js` (shared text normaliser), `detect-spam.js` (per-user event tracker, seven checks), `detect-links.js` (link and invite extraction, allow/block evaluation), `detect-words.js` + `words-default.js`, `strikes.js` (in-memory sliding-window store, `stepReached`, `isTopStep`; lost on restart), `exempt.js`, `pipeline.js` (`createEngine().handleMessage`: exempt check, then detect) and `enforce.js` (`enforce(ctx, {message|null, findings...})`: strike, delete, one `runAction` from `moderation/actions.js` for the most severe step, then history; shared by every source of findings: message rules, honeypot and native events), `nickname.js`, `events.js` (messageCreate/Update, memberAdd/Update, 60 s prune sweep), `history.js` (table `automod_history`, migration 007, newest 200 per guild), `commands.js` and `commands-lists.js` (`/automod`), `index.js`. Phase 2 adds: `regex-safe.js` (RE2 compile/match, per-guild cache), `age.js` (`passesAge`, applied to every rule before its detector), `role-effect.js` (timed role; job type `automod.removeRole`, key `<userId>:<roleId>`; exported as `jobs` from `index.js`), `honeypot.js` (`honeypotFinding`; the pipeline enforces a honeypot post alone, after the exemption check), `native.js` (`createNativeHandler`, `listNativeRules`; `events.js` listens to `AutoModerationActionExecution`, shares `engine.strikes`, intent `AutoModerationExecution` is set in `src/index.js`). `findings` are `{rule, reason}`; `RULES` is spam, invites, links, words, honeypot, native. The pipeline reuses moderation's `runAction`, `readConfig` and `canUseAction`, so warn and timeout steps make normal cases and mod log lines.
- **Autocomplete** (`routeInteraction` in `src/core/loader.js`): a command object may export `autocomplete(interaction, ctx)` next to `execute`; the router calls it for autocomplete interactions and answers an empty list if it throws. Used by `/embed` (`autocompleteEmbed`, managers only). Options need `.setAutocomplete(true)` and a redeploy (`npm run deploy`).
- **Context** (`src/index.js`): `ctx = { db, client, commands }`; `ctx.commands` is the loaded command map, used by `/help` to read command definitions.
- **Help** (`features/help/index.js`): `buildHelp`, `commandPaths`, `findFeature` walk command JSON to list subcommand paths.

## Graph hot spots
Most-connected nodes in the Graphify map: `t`, `guard()`, `ephemeral()`, `setFeature()`, `getFeature()`, `getLang()`, `sendLog()`. Changes there ripple widely.
