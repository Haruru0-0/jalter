# Architecture

Discord bot: discord.js 14, Node 22+, ESM, Postgres in Docker. Entry `src/index.js`; slash commands registered by `src/deploy-commands.js`.

## Layout
- `src/features/<name>/index.js` - one folder per feature; each is listed in `src/modules.js` (the loader's module list).
- `src/core/` - shared helpers: `guard.js`, `registry.js`, `toggle.js`, `permissions.js`, `replies.js`, `placeholders.js`, `mentions.js`, `send.js`, `lists.js`, `members.js`, `loader.js`, `scheduler.js`, `duration.js` (`parseDuration`, `formatDuration`; moved out of autorole).
- `src/db/` - `index.js` (pool, `resetDb()` for tests), `settings.js`, `migrations/` (001_init, 002_named_embeds, 003_autorole_tables, 004_scheduled_jobs, 005_autorole_to_scheduler, 006_mod_cases, 007_automod_history, 008_verification_overwrites, 009_reaction_roles).
- `src/i18n/` - `en.json`, `fr.json`, `ar.json`, and `index.js` with `t(lang, key, vars)` and `getLang`.

## Key pieces
- **Registry** (`core/registry.js`): `FEATURES` lists every feature with phase, command and enable command. Optional fields: `commands` (several top-level commands, e.g. `set` + `test`), `byKey` (a shared command like `/set` whose subcommands are split per feature key), `alwaysOn`. Phase 2-5 entries are "coming soon" stubs with `command: null`. `alwaysOn` features skip the enabled check.
- **Guard** (`core/guard.js`): `guard(interaction, ctx, key, {requireManager, requireEnabled})` checks guild-only, manager permission, and enabled state, replies ephemerally on failure, and returns the guild language on success. Almost every command handler starts with it.
- **Settings** (`db/settings.js`): `guild_settings(guild_id, feature, enabled, config jsonb)`. `getFeature` returns `{enabled:false, config:{}}` when no row; `setFeature` upserts and merges config.
- **Toggle** (`core/toggle.js`): shared `enable`/`disable` subcommands.
- **Scheduler** (`core/scheduler.js`, table `scheduled_jobs`: id, guild_id, type, key, payload jsonb, due_at, attempts, claimed_until; unique on guild_id+type+key): one shared, restart-safe job runner. Helpers `scheduleJob` (same guild+type+key updates the row, resets attempts; this needs a non-null key, since NULL keys never conflict and always insert a new row), `cancelJobs` (by guild, type, optional key, optional payload containment; with no key it matches any key), `claimDue`, `completeJob`, `failJob`. `startScheduler(ctx, registry)` ticks every 30 000 ms (timer is unref'd, a tick never overlaps the previous one) and `index.js` starts it inside the `ClientReady` handler, so nothing runs before the client is ready. Each tick runs every feature's `housekeeping` functions, then claims due jobs of registered types and runs their handlers. A feature adds job types by exporting `jobs` (`{ 'type': async (ctx, job) => ... }`) and per-tick functions by exporting `housekeeping` (`async (ctx, { now }) => ...`); `collectModules` in `loader.js` gathers both and throws on a duplicate job type. Handler contract and retry rules: see [[decisions]] and [[gotchas]]. Auto role is the first user: job type `autorole.grant`, handler `grantTimedRole`, housekeeping `purgeRememberedRoles` (sticky-role memory cleanup).
- **Moderation** (`features/moderation/`): `store.js` (tables `mod_cases` and `mod_counters`, migration 006; `createCase` takes the next per-guild number and inserts in one SQL statement; also warnings list/edit/deactivate/clear/top, `getCase`, `setCaseReason`, `setCaseLog`, `isCurrentlyMuted`), `config.js` (`readConfig` defaults, permitted roles), `rules.js` (`canUseAction`, `checkTarget` hierarchy, `checkDuration`), `actions.js` (`runAction` engine, job handlers `expireBan`/`expireMute`, `reapplyMute` on `GuildMemberAdd`), `format.js` (mod log embed and DM text), `commands-actions.js`, `commands-warnings.js`, `index.js` (the `/moderation` settings command; exports `commands`, `events`, `jobs`). `runAction` returns `{ok:true, modCase, warnings}` or `{ok:false, reason}`; `warnings` may hold `dm_failed`, `case_not_saved`, `log_failed`, `schedule_failed`. Timed actions are scheduler jobs `mod.unban` and `mod.unmute` (key = user id, payload `{userId}`).
- **Channel tools** (`features/moderation/`): `tools-common.js` (`checkToolAccess` checks `canUseAction`, channel type, that the member can view the channel, and that the bot holds ViewChannel plus the action permission and extras; `postNotice`; `logTool` writes one `modAction` line and never throws), `channel-move.js` (`moveChannelId` rewrites a channel id in the `logging`, `greet`, `leave`, `boost` and `media` settings rows inside one transaction with `FOR UPDATE`; `mediaHoldsChannel`), `commands-channel.js` (`/slowmode`, `/lock`, `/unlock`), `commands-purge.js` (`/purge messages|channel`, pure `selectPurgeTargets`, button handler with prefix `purge`). `ACTION_PERMISSIONS` in `rules.js` gained `purge` (ManageMessages) and `purgeall`, `slowmode`, `lock`, `unlock` (ManageChannels). They create no cases. See [[features-built]].
- **Mod log**: `sendLog` (logging) now returns `{channelId, messageId}` where it posted, or `null`. Moderation posts through the hidden event `modAction` (`HIDDEN_EVENTS` in `logging/events.js`, `categoryOf` maps it to the `mod` category), which is not in `EVENTS`, so it is not a `/logging event` choice. The returned ids are stored on the case so `/reason` can edit the message.
- **Auto-mod** (`features/automod/`): `config.js` (`readConfig` defaults and list/step mutators), `normalize.js` (shared text normaliser), `detect-spam.js` (per-user event tracker, seven checks), `detect-links.js` (link and invite extraction, allow/block evaluation), `detect-words.js` + `words-default.js`, `strikes.js` (in-memory sliding-window store, `stepReached`, `isTopStep`; lost on restart), `exempt.js`, `pipeline.js` (`createEngine().handleMessage`: exempt check, then detect) and `enforce.js` (`enforce(ctx, {message|null, findings...})`: strike, delete, one `runAction` from `moderation/actions.js` for the most severe step, then history; shared by every source of findings: message rules, honeypot and native events), `nickname.js`, `events.js` (messageCreate/Update, memberAdd/Update, 60 s prune sweep), `history.js` (table `automod_history`, migration 007, newest 200 per guild), `commands.js` and `commands-lists.js` (`/automod`), `index.js`. Phase 2 adds: `regex-safe.js` (RE2 compile/match, per-guild cache), `age.js` (`passesAge`, applied to every rule before its detector), `role-effect.js` (timed role; job type `automod.removeRole`, key `<userId>:<roleId>`; exported as `jobs` from `index.js`), `honeypot.js` (`honeypotFinding`; the pipeline enforces a honeypot post alone, after the exemption check), `native.js` (`createNativeHandler`, `listNativeRules`; `events.js` listens to `AutoModerationActionExecution`, shares `engine.strikes`, intent `AutoModerationExecution` is set in `src/index.js`). `findings` are `{rule, reason}`; `RULES` is spam, invites, links, words, honeypot, native. The pipeline reuses moderation's `runAction`, `readConfig` and `canUseAction`, so warn and timeout steps make normal cases and mod log lines.
- **Verification** (`features/verification/`, spec `docs/tiered-powers/specs/2026-10-17-verification-design.md`): `config.js` (`readConfig`, `MODES` button/captcha, `STATES`, `classify` = verify > public > skip > gated), `plan.js` (pure bigint permission planner: `planChannel`, `everyonePerms`, `canEveryoneView`, `roleViewers`), `apply.js` (`gateChannel` / `revertChannel`, the Discord edge, both working on a forced fetch of the channel (`liveChannel`); `snapshotOf`), `store.js` (undo records, table `verification_overwrites`, migration 008), `rollout.js` (job handlers and `startRollout`), `verify.js` (`verifyMember`, `postPanel`, the button and captcha handlers, `handle`), `captcha.js` (in-memory challenge store) and `captcha-image.js` (`renderCaptcha`), `commands.js` (setup, status, remove, builder) and `commands-lists.js` (mode, public / skip lists, verify, unverify), `events.js` (`GuildMemberAdd` for bots, `ChannelCreate`), `log.js` (`logVerification`).
- **Verification rollout** (scheduler job types `verification.grant` then `verification.gate`, both key `rollout`, so scheduling twice replaces the row): the grant job gives Verified to members who joined before `cutoff`, 20 per batch with a 20 s time budget, then sets `grantDone` and schedules the gate job; the gate job (10 channels per batch, categories first, snowflake order) refuses to run until `grantDone` is true. States in the config: `none` -> `rolling_out` (setup) -> `active` (all channels gated) or `failed` (some channels failed, or the final scheduler attempt gave up; `failedChannels` holds the count and `failedChannelIds` the first 10 ids, both carried in the gate job payload between batches). Concluding is one conditional UPDATE from `rolling_out`, so it runs once; on the final attempt (`MAX_ATTEMPTS`) an error concludes the rollout as `failed` instead of retrying. `startRollout` can also resume a `failed` or job-less `rolling_out` rollout with the original cutoff (only the gate if `grantDone`), but nothing calls it that way yet: setup refuses unless the state is `none`, so after `failed` the way forward is `/verification remove` and setup again.
- **Verification undo record**: `verification_overwrites(guild_id, channel_id, everyone, verified, bot jsonb, created_at)`. Each of the three is `{existed, allow, deny}` (bit strings) or null when the gate did not touch that target; `existed:false` means the overwrite did not exist and is deleted on revert if only gate bits remain. `recordOriginal` is `ON CONFLICT DO NOTHING`: the first record per channel wins, so a re-gate never overwrites the true original. `revertChannel` only changes the gate's own bits and deletes the record afterwards; the record holds no role id (Verified is read from the config).
- **Verification components**: one component prefix `verification` (`components: {prefix: 'verification', handle}` in `commands.js`). customIds: `verification:go` (the Verify button, also "verify again"), `verification:enter:<userId>` and `verification:code:<userId>` (captcha button and modal), `verification:setup:ok:<userId>:<createdAt>` / `verification:setup:no:<userId>`. The captcha image reuses `@napi-rs/canvas` and `ensureFonts` exported from `features/greet/card.js`; no new dependency.
- **Verification unverified policy** (`unverified.js`, `unverified-jobs.js`, `unverified-commands.js`; design `docs/tiered-powers/specs/2026-10-19-verification-unverified-policy-design.md`): config keys `unverifiedPolicy` (`none`|`kick`|`warn_kick`, default `none`), `kickAfterSeconds` (default 86400, 600 to 2592000) and `warnAfterSeconds` (null = half the kick time; for `warn_kick` at most kick time minus 600 s). `GuildMemberAdd` in `events.js` calls `queueUnverifiedJobs` for humans only while verification is running (`rolling_out`/`active`/`failed`) and the policy is not `none`; `GuildMemberRemove` and a successful `verifyMember` call `cancelMemberJobs`. Scheduler job types `verification.warn` (only for `warn_kick`) and `verification.kick`, both keyed by member id, so a rejoin replaces them. Due times count from the join, never before now. The payload carries `policy`, `kickAt` and `kickAfter` as queued, so later policy or time changes never touch queued members; `policy:none` (`executeUnverified`) and `/verification remove` call `cancelAllUnverifiedJobs`. At fire time `load` re-reads feature on, running state, policy not `none`, member present, not a bot, no Verified role, and `isSpared` (bot, owner, at or above the bot's top role, `canManage`). The warn job claims itself first (deletes its own row, zero rows means someone else owns it), then calls `runAction` (type `warn`, actor the bot) once, then `rescheduleKick` writes `warned: 'ok'|'failed'` into the kick row in one statement; the kick job under `warn_kick` kicks only on `warned === 'ok'`. A warn that fires late leaves at least 600 s before the kick (`kickAfterWarn`). A refused kick writes one `unverified_failed` line through `logVerification` and is not retried; a thrown error is rethrown for the scheduler to retry.
- **Anti-raid** (`features/antiraid/`, spec `docs/tiered-powers/specs/2026-10-19-antiraid-design.md`): `config.js` (`DEFAULTS`, `RANGES`, `readConfig` normalises the stored config, `checkConfig` validates a patch, `resolvePingRole` picks the ping role), `joins.js` (`createJoinStore`: the recent joins of every server, in memory only; `record` returns how many joins are inside the window, `recent`, `clear`, `prune`; a 60 s prune sweep, `startAntiraidSweep`), `lockdown.js` (`startLockdown`, `endLockdown`, `kickYoungJoin`, the end job), `events.js` (the `GuildMemberAdd` detector), `commands.js` (`/antiraid enable|disable|config|status|start|end`), `index.js` (exports `commands`, `events`, `jobs`). The settings and the state of a running lockdown live together in the `antiraid` feature config (merge-written with `setFeature`, no table, no migration): the keys `joins`, `windowSeconds`, `accountAgeSeconds`, `durationSeconds`, `pingRoleId` and the state keys `state`, `lockedAt`, `lockedUntil`, `startedBy`, `kicked`, `invitesPausedByUs`, `inviteResult`, `alertResult`. A start flips the state with ONE conditional UPDATE (`state` not already `locked` and the feature on), so two starts can never both win; an end is the same trick in reverse and is idempotent. The end timer is a scheduler job of type `antiraid.end`, key `lockdown`. The kicks go through moderation's `runAction` (type `kick`, the bot as actor) and reuse verification's `isSpared` and `fetchMember`; a member with the Verified role is not spared. The invite pause is Discord's own (`guild.setIncidentActions({invitesDisabledUntil})`, it needs Manage Server and is capped at 24 hours); only a pause this lockdown made is lifted at the end. The alert is one `sendLog` mod-log line plus a second message that pings one role.
- **Reaction roles** (`features/reactionroles/`, spec `docs/tiered-powers/specs/2026-10-20-reaction-roles-design.md`; registry entry `reactionroles` with command `reactionroles`, listed last in `src/modules.js`). Files: `config.js` (`STYLES`, `TYPES`, `MAX_ENTRIES` 20, `SELFDESTRUCT_JOB`, `parseEmoji`, `emojiKey`, `componentEmoji`, `typeAllowedForStyle`), `rules.js` (pure `decidePick` for reactions and buttons and `decideMenu` for dropdowns: gate order lock, blacklist, whitelist, then type, binding, limit), `apply.js` (`applyPick` serializes per `messageId:memberId` with `serialize` from `core/auto-channel.js`, decides on a forced member fetch, re-checks `isDangerousRole` and `botCanGive`, changes roles one at a time with single-role calls (adds first, undone on a partial failure), stores the binding row, and `createGrantAlert` throttles the staff alert to once an hour per message), `store.js` (messages, entries, bindings; `removeRoleFromLists` strips a deleted role from every whitelist and blacklist of a guild), `render.js` (`buildComponents`, `syncMessage`, `postRoleMessage`, `refreshEmbed`), `setup.js` (`checkRoleForSetup`, `missingBotPermission`, `addOne`, shared by `add` and the builder), `builder.js` (panel), `components.js` (one component prefix `reactionroles`; customIds `reactionroles:btn:<messageId>:<entryId>`, `reactionroles:menu:<messageId>`, `reactionroles:b:*` for the builder, `reactionroles:purge:*`), `commands.js` and `commands-settings.js` (subcommands; settings ones plus the `reactionroles.destruct` job), `events.js` (`MessageReactionAdd/Remove`, `MessageDelete`, `MessageBulkDelete`, `GuildRoleDelete`, `ChannelDelete`, `GuildMemberRemove`), `log.js` (mod-log lines through the hidden `modAction` event). Tables (migration 009): `reaction_role_messages` (message_id primary key, style, type, `limit`, whitelist and blacklist jsonb, selfdestruct_at, embed_name null for adopted), `reaction_role_entries` (cascade on message delete; unique per message on role and on emoji), `reaction_role_bindings` (message_id + user_id primary key). Job type `reactionroles.destruct` (key = message id). Needs the `GuildMessageReactions` intent and `Partials.Reaction` in `src/index.js`.
- **Autoresponder** (`features/autoresponder/`, stages 1 to 3 and the builder built on `phase-3` (manual testing pending), registered in `modules.js` after auto-mod and in `registry.js` (`autoresponder`, enable command `autoresponder enable`), design `docs/tiered-powers/specs/2026-10-24-autoresponder-design.md`): migration 010 creates `autoresponder_rules` (trigger, match_mode, script, `compiled` jsonb, enabled) and `autoresponder_cooldowns` (rule_id cascade, user_id, until); both are in the `resetDb` TRUNCATE list. `store.js` holds the rule SQL; `createRule` takes `pg_advisory_xact_lock(hashtext('autoresponder:<guildId>'))` before counting so two concurrent creates cannot pass the 100-rule cap. `cache.js` keeps the enabled rules per server in memory (an empty list for a server with the feature off), so a message costs no database read after the first. A per-server generation counter makes `invalidate` win over a load that is still in flight, so a stale snapshot is never cached. `match.js` holds the pure matching (`checkTrigger`, `matchRule`, `chooseRule`). The script pipeline starts in `script/`: `parse.js` (`parseScript`, hand-written scan, never throws), `functions.js` (a table of function name to `{min, max, check}`; stage 2 added its functions as new rows), `placeholders.js` (`PLACEHOLDER_NAMES`, `buildScriptVars`) and `evaluate.js` (pure `evaluate(compiled, ctx)`: gates, then the rendered text; the cooldown gate is left to the handler), `execute.js` (`executePlan` runs a plan against Discord in a fixed order, one try/catch per step, role changes by single-role calls, `allowedMentions` never allows roles or everyone; `throttle.js` and `log.js` give the in-memory throttles and the `modAction` mod-log lines), `cooldown.js` (`claimCooldown` is one atomic INSERT ... ON CONFLICT DO UPDATE ... WHERE until <= now, so two simultaneous messages cannot both pass; `pruneCooldowns` is the housekeeping function), `events.js` (the `MessageCreate` handler; it skips bots, webhooks, system messages, DMs and the bot itself, picks one rule with `chooseRule`, then waits on `core/message-outcome.js` to learn whether auto-mod acted on the message), `commands.js` (`/autoresponder enable|disable|add|edit|editmatchmode|toggle|remove|list|show|test` (`test` is a read-only dry run: store reads, `chooseRule`, `evaluate`, no `executePlan`, no cooldown claim, no log line); `add` and `edit` open a modal, customIds `autoresponder:m:add:<match>` and `autoresponder:m:edit:<id>`, and the submit compiles the script with the submitting member as writer and re-checks the manager guard), and `compile.js` (`compileScript` resolves roles, channels, users and emoji to ids at save and returns a JSON-safe `compiled`; `COMPILE_ERROR_CODES` lists every error code).
- **Autoresponder builder** (`features/autoresponder/builder/`, built on `phase-3`, manual testing pending, design `docs/tiered-powers/specs/2026-10-24-autoresponder-builder-design.md`): `/autoresponder builder` opens an ephemeral panel that creates NEW rules only (the other subcommands, including `edit`, are unchanged). `draft.js` (immutable draft ops; `toScriptMode`), `generate.js` (`generateScript`: reply text verbatim, then one function per line; `escapeArg` escapes `\` and `|`; a script-mode draft returns its `scriptText`), `drafts.js` (in-memory panel store: 8-character panel ids, one panel per member per server, 15-minute sliding expiry, 500-panel cap, a save lock `beginSave`/`endSave`, lost on restart), `summary.js`, `panel.js` (custom ids `autoresponder:b:<action>:<userId>:<panelId>[:<extra>]`, at most 100 characters; `PAGES` = basics, reply, conditions, actions, random, review; a separate embed view; a script-mode payload), `handlers.js` (`handleBuilder` checks the opener, the manager guard and the panel on every click and modal submit, in that order; `tryChange` applies a change, compiles the generated script with the pressing member as writer and reverts it with the compiler's own errors on failure, so the compiler is the only place the limits live). Reply page: text, destination (reply, DM, channel), delete trigger, silent, embed (none, plain colour or a stored embed: the select lists `none`, `plain` and the first 23 named embeds) and delete-reply seconds. Conditions: all eight gates, up to 25, a role gate accepts any role. Actions: the five role, nickname and reaction actions; the compiler refuses dangerous roles. Try it (`btry`/`mtry`) compiles the draft and shows `matchRule` plus `describeRun` for a sample message; it reads only. Edit script text (`bscript`/`mscript`) compiles hand-edited text and switches the draft to script mode for good; script mode then accepts only the actions in `SCRIPT_MODE_ACTIONS` (trigger, mode, basics, back, try, script edit, save, cancel) and redraws the panel for any other. A `}` is refused in the cooldown seconds, permission name, nickname, emoji, colour and delete-reply seconds because the parser has no escape for it inside an argument (reply text and trigger are not checked: a lone `}` is plain text there); a typed permission name with `|` is refused. Save and Try it refuse a channel destination with no channel (`needChannel`). Save re-checks the trigger, compiles, calls `createRule` (so the 100-rule cap holds), invalidates the cache and writes one `add` mod-log line marked as made with the builder. The dry run behind `/autoresponder test` lives in `dryrun.js` (`describeRun`), shared with Try it.
- **Autoresponder stage 2** (built on `phase-3`, manual testing pending, checklist section 16 "Stage 2"; design `docs/tiered-powers/specs/2026-10-24-autoresponder-stage2-design.md`; plan `docs/tiered-powers/plans/2026-10-24-autoresponder-stage2.md`): random values and the member's words. Files: `parse.js` recognizes only the exact bracket tokens (`[$N]`, `[$N+]`, `[$N-M]`, `[range]`, `[choice]`, `[lockedchoice]`, numbers 2 to 4 for the random ones; any other `[...]` stays literal text, `\[` is never a token), `match.js` `triggerRemainder` (the original text after the trigger for `startswith` and `includes`, folded the same way `matchRule` folds so words never shift), `script/args.js` (`parseWords`, `renderArg`, `renderArgsInText`, `checkArgType`) and `script/random.js` (`drawRandom` with an injectable random source). `compile.js` is two-pass (functions first, then tokens and role targets, so script order never matters) and writes `compiled.version` 2 with `random`, `argChecks` and role action `target`; a random token is live only when the script defines its function. A role target needs `{requirearg:N|user}` for that N and a `{requirerole}` or `{requireperm}` in the script. At run time `script/run.js` `prepareRun` computes the words, draws every random value once and checks every `{requirearg}` word against the server; `evaluate` renders the `arg`/`rand` parts and returns a skip with `gate: 'arg'` (one `autoresponder.notice.arg` notice, before the cooldown is claimed) when a check fails; `allowedUsers` holds only words checked as `user`, so member-typed mentions never ping; `executePlan` changes the role on the checked target (`TARGET_MISSING`, `TARGET_UNSAFE` skip it, the rest of the script runs). `/autoresponder test` and Try it go through `describeRunFor` and `prepareRun`. The dry run (`dryrun.js`, `describeRun`) lists a `requirearg N` gate line, a "Random values drawn" line and a "Would ping" line. The builder has a Random page (add and remove range, choose, weightedchoose, lockedchoose), a `requirearg` condition ("Needs a word after the trigger", word 1 to 20 and a type) on the Conditions page and a target select on role actions (the sender or the member in word N); all go through `tryChange` and the compiler stays the only place the limits live. Limits: 4 `range`, 4 `choose`/`weightedchoose` and 4 `lockedchoose` per script, 25 options per choice, `range` ends at most 1000000000 in size, words 1 to 20. Rules compiled by stage 1 stay version 1 and keep running; no migration. `COMPILE_ERROR_CODES` gained RANGE_INVALID, WEIGHT_INVALID, TOO_MANY_RANDOM, CHOICE_COUNT_MISMATCH, CHOICE_NOT_CHOSEN_YET, ARG_INDEX_INVALID, ARG_TYPE_INVALID, NO_ARGUMENTS_IN_MODE, TARGET_NOT_CHECKED_USER and TARGET_NEEDS_GATE; `RUN_ERROR_CODES` gained TARGET_MISSING and TARGET_UNSAFE.
- **Autoresponder stage 3, buttons** (built on `phase-3`, manual testing pending, checklist section 16 "Buttons"; design `docs/tiered-powers/specs/2026-10-31-autoresponder-stage3-design.md`, plan `docs/tiered-powers/plans/2026-10-31-autoresponder-stage3.md`): migration 011 creates `autoresponder_buttons` (stored buttons per server, unique by name, at most 50 per server), `autoresponder_button_messages` (one record per posted message: buttons, invoker, original words and random results, `locked`, `pressed`, `expires_at`; cascades from the rule) and `autoresponder_button_cooldowns` (message, button index, user; cascades from the record). `buttons/store.js` holds the CRUD (`createButton` takes an advisory lock before counting, like `createRule`), `getMessageRecord` (null once expired), `claimPress`, `claimButtonCooldown` and `pruneButtonMessages` (in the housekeeping list with `pruneCooldowns`; records live 14 days, `BUTTON_TTL_MS` in `execute.js`). `buttons/model.js` is pure: `buildRows` (5 per row, 25 at most; link buttons have no custom id and are never disabled), `buttonId`/`parseButtonId` (`autoresponder:p:<messageId>:<index>`, the index into the record's `buttons` list identifies the button), `pressDecision` and `createPressThrottle` (3 seconds per presser per message, in memory, bounded at 10000). `buttons/setup.js` is `/autoresponder button add|edit|remove|list` (a `button` subcommand group in `commands.js`): `add` and `edit` open a modal whose custom id carries the name, colour and the `invoker_only`/limitation flags (`autoresponder:m:btnadd|btnedit:<name>:<style>:<flags>`, re-validated on submit; the submit compiles the script with `buttonScript: true`), and each change writes a `btnadd`/`btnedit`/`btnremove` mod-log line. The compiler knows `{addbutton:name}` (the stored button must exist at save) and `{addlinkbutton:label|url[|emoji]}` (http or https, 512 characters), up to 25 per reply in script order, and refuses `{dm}` with a button (`BUTTONS_NEED_CHANNEL`) and a button reply with no text and no embed (`BUTTONS_NEED_TEXT`); a button's own script compiles with `env.buttonScript` (random tokens always live, no match mode). Sending: `executePlan` returns `{ errors, sent }`; when a reply has buttons it resolves each stored button fresh (a missing one is skipped with `BUTTON_MISSING`), stores the message record and then edits the buttons onto the sent message, so a press can never find buttons without a record. A press (`buttons/press.js`, no manager guard, `deferUpdate` first) checks, in this order: the feature is on, the record is alive and belongs to this server, message and channel, the rule exists and is enabled, the stored button exists, then `pressDecision` (the 3-second throttle first, then `invoker_only`), then `evaluate` on the button script with the stored words re-checked and the stored draws merged (a failed gate or word answers a notice and claims nothing), then the claim, then `{cooldown}`, then `executePlan` posts the reply publicly as a reply to the button message. The claim is one atomic statement per limitation: `none` writes nothing but is refused when the message is locked, `limited` appends the index to `pressed` once, `strict` sets `locked` (the whole message). After a `limited` or `strict` claim the buttons are re-rendered from the record (a stored button removed since is shown disabled). A chained reply (a button script that attaches buttons) stores a new record with the presser as invoker and copies the words and draws (`buttonState`). The builder has a Buttons page (`PAGES` ends `random`, `buttons`, `review`): a select of the first 24 saved buttons (`pbtn`), an Add link button form (`blink`/`mlink`) and a remove select (`rmbtn`), all through `tryChange`. `COMPILE_ERROR_CODES` gained BUTTON_NOT_FOUND, LINK_URL_INVALID, TOO_MANY_BUTTONS, BUTTONS_NEED_CHANNEL, BUTTONS_NEED_TEXT and BUTTON_NAME_INVALID; `RUN_ERROR_CODES` gained BUTTON_MISSING.
- **Autocomplete** (`routeInteraction` in `src/core/loader.js`): a command object may export `autocomplete(interaction, ctx)` next to `execute`; the router calls it for autocomplete interactions and answers an empty list if it throws. Used by `/embed` (`autocompleteEmbed`, managers only). Options need `.setAutocomplete(true)` and a redeploy (`npm run deploy`).
- **Context** (`src/index.js`): `ctx = { db, client, commands }`; `ctx.commands` is the loaded command map, used by `/help` to read command definitions.
- **Help** (`features/help/index.js`): `buildHelp`, `commandPaths`, `findFeature` walk command JSON to list subcommand paths.
