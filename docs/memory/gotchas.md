# Gotchas

- `stickyroles` is still a "coming soon" stub in `core/registry.js`, but `/autorole reassign` and `/autorole blacklist` already do it. Remove the stub or point it at `/autorole`.
- The bot's highest role must sit above any role it gives, or Discord refuses (autorole).
- Privileged intents needed: Server Members and Message Content. Guilds, Guild Messages, Guild Expressions, Guild Moderation and Guild Voice States are not privileged.
- Invite permissions: View Channels, Send Messages, Read Message History, Embed Links, Attach Files, Manage Roles, Kick Members, Ban Members, Moderate Members (the last three came with moderation), plus Manage Messages and Manage Channels (channel tools; see below). Manage Nicknames was added with auto-mod (README and setup guide updated). The `GuildMessageReactions` intent is still not added (reaction roles, starboard need it).
- `DEV_GUILD_ID` set means commands register to that one server only and update instantly; unset means global (slow to propagate).
- Setting a feature's config merges into existing jsonb (`setFeature`), it does not replace it.
- `graphify-out/` can be stale; compare its commit with `git rev-parse HEAD`.
- Logging config shape (in the `logging` feature row): `channels{category:id}`, `disabledEvents[]` (everything is on once a channel resolves), `ignore{channels[],members[],prefixes[]}`. `setFeature` shallow-merges top-level keys, so always write the whole nested object (`channels`, `ignore`), never a partial one.
- Logging channel lookup: `channels[category]`, else for the `join` category `channels.members` (old join/leave logs keep working), else `channels.default`, else nothing.
- Logging ignore lists only affect message events (delete, edit, purge, invite posted). Events inside a log channel are never logged (loop guard).
- Logging "By" needs View Audit Log; it is optional and the invite list does not require it. `/logging setup` needs Manage Channels and is not idempotent: a second run adds a new "Logs" category.
- Logging "By" lookups are lazy: handlers pass `opts.executor` (an async function) to `sendLog`, which calls it only after the enabled, event, ignore, channel and loop-guard checks pass. Timeout attribution filters audit entries on the `communication_disabled_until` change; ban handlers use `ban.user` without fetching (gateway bans are always partial). Channel create/delete/update do not use the loop guard, so changes to log channels are themselves logged.
- Moderation cases are logged to the `mod` logging category through the hidden `modAction` event. If logging is off or no `mod` channel resolves, `sendLog` returns `null`: the action still succeeds but the case has no stored log message (so `/reason` cannot edit one). See [[roadmap]].
- Setup and testing docs: `docs/discord-bot-setup.md` (developer portal, intents, invite, `.env`, troubleshooting) and `docs/testing-checklist.md` (tick-box manual test per feature). When a feature or invite permission changes, update both and the README manual check. `/help` needs no edit for new subcommands: it reads the command definitions.
- Repo hosting: `origin` is the private GitHub repo `Haruru0-0/jalter` (branches `autorole-upgrade`, `phase-1`). Commits use the global git identity (Haru); no Co-Authored-By trailers. History was rewritten once on 2026-10-14 before the first stable push; local tags `backup-before-rewrite-*` hold the old history and can be deleted.
- Scheduler handlers must be idempotent (at-least-once: a crash or expired claim can run a job twice) and must return, not throw, on permanent Discord errors (HTTP 4xx other than 429, unknown member or role, missing permission); throwing means retry, and after 5 attempts the job is dropped. A feature adds a job type by exporting `jobs` from its module; `collectModules` throws on duplicate types. A job type nobody registered just sits in `scheduled_jobs` (see [[architecture]], [[decisions]]).
- Timed roles no longer have a `pending_roles` table: they are `scheduled_jobs` rows of type `autorole.grant` with key `userId:roleId` and payload `{userId, roleId}`.
- `/logging event` already has 25 choices (the Discord limit), so the mod log uses a hidden `modAction` event outside `EVENTS` (`HIDDEN_EVENTS`, `categoryOf`).
- GitLab mirror: `scripts/mirror-to-gitlab.sh` adds `.github/workflows/mirror-to-gitlab.yml` to each local repo (default list: jalter, Nebula, PortaGen, aesthetic-portfolio-os, notioncraft-ai, steam-games-analysis; not career-ops) and sets the `GITLAB_TOKEN` secret. Mirrors GitHub to `gitlab.com/Haruru0-0/<repo>` on every push and nightly; GitLab copies are read-only (overwritten). New repo: run the script with its name. The script prints progress and shows its prompts with printf (works without a TTY; token input is hidden, nothing echoes). It reads the token from `$GITLAB_TOKEN`, then the Windows credential vault (saved on request after the first prompt; `--forget` deletes it), then prompts. Status: ran for jalter and Nebula; PortaGen, aesthetic-portfolio-os, notioncraft-ai and steam-games-analysis still need a rerun. PortaGen history was scrubbed of a leaked Supabase DB password by another session (rotate the password).
- Moderation: the DM to the target goes out before the Discord action for every punishment (warn, timeout, mute, kick, ban), so a refused action can still have sent a DM. `/unban`, `/untimeout`, `/unmute` send none.
- Moderation: the "already muted" check decides by the latest `mute`/`unmute` case of the user (`isCurrentlyMuted`). `expireMute` skips only when that latest case is a mute that is still running (permanent, or ending more than 1 s from now), so a newer mute keeps the role. Otherwise it fetches the member and does nothing if they left or no longer have the mute role; if they still have it, it removes it and writes the bot's "expired" unmute case. So a timed mute whose case failed to save still expires, and a rerun never logs a second case. A manual `/unmute` or `/unban`, and a new permanent mute or ban, cancel the older expiry job.
- Moderation: the action commands treat only Discord error 10007 (Unknown Member) from the member lookup as "not in the server"; any other lookup error is rethrown (the router answers `common.error`), so hierarchy checks are never skipped by a failed lookup. A missing permission replies `moderation.err.not_allowed`.
- Moderation: durations are at least 1 minute and at most 10 years (315 360 000 s) for any action, 28 days for a timeout (`checkDuration`, `too_long`); the `duration` option is at most 32 characters. The cap keeps `ends_at` storable, since the Discord action runs before the case is saved.
- Moderation: `/reason` updates the case, then edits the stored mod log message best effort (a deleted message or channel is ignored). `/warnings edit` changes the reason only in the database.
- Moderation: `mod.unban` and `mod.unmute` handlers run whether or not the feature is enabled; the rejoin mute (`reapplyMute`) needs the feature on and a mute role that still exists. `kick`, `timeout`, `untimeout`, `mute`, `unmute` need the user to be in the server; `warn`, `ban`, `unban` work by user ID.
- Moderation: new commands only appear after `npm run deploy`, and migration 006 (`mod_cases`, `mod_counters`) runs on the next bot start.
- Auto-created channels (`src/core/auto-channel.js`, needs Manage Channels): logging makes `<category>-logs` (or `logs`) in a private "Logs" category (id kept in `config.categoryId`) when an event has no category or default channel; greet/leave/boost make `welcome`/`goodbye`/`boosts` when a message is saved or a member event fires with the kind on and no `channelId`. A chosen channel is never replaced, and a configured channel that was deleted is not recreated (logs drop with a warning, greet gives `no-channel`). Logging creation is serialized per guild (all categories share the Logs category and the saved config), greet creation per guild and kind (`singleFlight`); a channel made but not saved is deleted again. `/logging clear <category>` with no default channel is followed by a fresh auto-created `<category>-logs` on the next event. Failure only warns, and a failed attempt makes that key skip further tries for 10 minutes (in memory, reset on restart; a success clears it). See [[features-built]].
- Channel tools: `/purge channel`, `/slowmode`, `/lock` and `/unlock` need Manage Channels; lock, unlock and purge channel also need the bot to hold Manage Roles (editing overwrites). None of the channel tools require Send Messages: an @everyone Send Messages deny (what `/lock` sets) applies to the bot too unless it is Administrator or has its own allow overwrite, so requiring it made `/unlock` refuse every locked channel. Notices are best effort; `/lock` posts its notice before applying the deny and deletes it if the deny fails. `/purge messages` needs Manage Messages and Read Message History; slowmode in a thread needs Manage Threads. The invite lists now include Manage Messages and Manage Channels (no longer optional). New commands need `npm run deploy`. See [[features-built]].
- Channel tools: a permitted-role holder may run `/purge channel` even without Manage Channels (the bot's own permissions are still checked). `/unlock` cannot tell its own @everyone Send Messages deny from one an admin set by hand, so it clears any such deny.
- Channel tools: a whole-channel purge changes the channel id. `moveChannelId` repoints the logging channels (and the logging ignore list) and the greet, leave, boost and media `channelId` in one transaction; stored mod-log message links to the old channel are not moved and stop working. A channel holding `media_items` is refused. The reason typed with `/purge channel` is held in memory until Confirm and is lost on restart. Purge messages scans at most 500 recent messages and skips pinned and over-14-day ones. See [[decisions]].
- Auto-mod: strikes live in memory (`strikes.js`) and reset when the bot restarts; only the history table is stored. The invite resolver fails open: if `fetchInvite` errors or times out the invite is allowed for that message. A refused top step (hierarchy, missing permission) still resets that rule's strikes.
- Auto-mod known gaps: in links `blockAllExceptAllowed` mode a bare `word.tld` in normal text can be flagged as a link. Invite lookups fail open (a failed `fetchInvite` lets the invite through). Fixed: `ptb.`/`canary.`/`www.` invite hosts, zero-width characters, soft hyphen and tatweel in `normalizeText`, and spam attachment/link-rate false positives from a sticky window.
- Auto-mod: new `/automod` commands need `npm run deploy`, migration 007 runs on the next start, and members with Manage Server, the bot manager role, Moderate Members or a moderation permitted role are never checked. Invite permissions now also include Manage Nicknames (nickname check).
- Auto-mod Phase 2: `re2` has an install script; on a deploy host without the prebuilt binary it needs a toolchain/GitHub access, and a strict npm may need `npm install-scripts approve re2`. Node must match `^22.22.2 || ^24.15.0 || >=26.0.0` (the range `re2` declares, so Node 23 and Node 24 before 24.15 are out). Patterns are not re-validated when read from storage (bad ones are skipped with a warning).
- Auto-mod timed role: needs Manage Roles and a role strictly below the bot's top role (checked at `/automod role` and again when granting); managed roles and @everyone are refused. Only members passed to `enforce` get it, so nothing happens if the member already left.
- Auto-mod honeypot: setting `/automod honeypot` does not enable the rule; run `/automod rule rule:honeypot state:on`. The bot needs View Channel and Manage Messages in the trap channel. A deleted channel just never matches.
- Auto-mod native: the bot needs Manage Server to list rules and to receive executions, and the `AutoModerationExecution` intent. Blocked messages have no message id, so the 5 s dedupe key falls back to the content (`ruleId:userId:c:<content>`): the Block, Alert and Timeout events of one hit count once, two different blocked messages count twice, but the same blocked text sent twice within 5 s counts once. `/automod native list` cannot tell missing permission from no rules. Native `delete` is off by default.
- Auto-mod honeypot: only a new post trips it. `MessageUpdate` (edits, embed unfurls, pins) reaches the pipeline with `edited: true`, and the honeypot skips those, otherwise each update would re-punish the member.
- Auto-mod timed role: a role with staff permissions (Administrator, Manage Server, Manage Roles, Ban, Kick, Moderate Members, Manage Channels, Manage Messages, Manage Webhooks, Mention Everyone) is refused at `/automod role` and again at grant time (console warning, not given), since bot-manager-role holders pass the guard without Manage Roles. Setup also needs the caller's top role above the role, unless they own the server.
- Auto-mod strikes (message, honeypot and native) live in memory and are lost on restart; only history is stored.
- Invite permissions now also include Manage Server (optional, only for the auto-mod `native` rule); Manage Roles is also used by the auto-mod timed role. `docs/discord-bot-setup.md` is updated.
- Auto-mod regex: `re2` is imported at module top level, so a missing native binary stops the whole bot at startup (fail-fast) rather than disabling only the regex checks.
- Auto-mod timed role: the staff-permission check looks at the role's server-wide permissions only; channel overwrites are not considered.
- Role safety: `src/core/role-safety.js` holds `isDangerousRole`, `callerCanGive` and `botCanGive` (auto-mod's `role-effect.js` re-exports them). `/automod role` and, at setup only, `/autorole add` and `/autorole timed add` refuse @everyone, managed, at-or-above-the-bot, staff-permission and at-or-above-the-caller roles (the owner is exempt from the caller check). Autorole grant time is unchanged: roles already configured keep being given, even if they now look unsafe or sit above the bot, and `/autorole show` still marks too-high ones. Re-adding an already listed role only re-enables the feature and is not rechecked.
- Verification gate rule: only channels `@everyone` can view are changed. "Can view" is computed from the guild-level `@everyone` permissions plus its own channel overwrite (`everyonePerms`); other roles and member overwrites are ignored, and Administrator on @everyone means every bit. Private channels are left untouched. A public channel gives Verified back only the bits @everyone had before (the allow is capped), so the gate never opens more than @everyone had.
- Verification write order (`gateChannel`): bot overwrite first (verify channel only), Verified next, @everyone last. Once @everyone is denied View a rerun would call the channel private and skip it, so doing it last lets a half-done channel be finished on rerun. Each write moves only the gate's bits and keeps the rest.
- Verification undo: the first record per channel wins (`ON CONFLICT DO NOTHING`), so changing a list re-applies from the original, not from the gated state (revert from the record, then gate with the new lists). Record shape and `existed:false` are in [[architecture]]. `/verification remove` keeps the record of any channel it could not restore and reports those channels; fix permissions and run it again.
- discord.js 14 overwrite cache: `permissionOverwrites.edit/delete` only call the API; `permissionOverwrites.cache` changes when the CHANNEL_UPDATE event arrives, and `edit()` merges onto the cached overwrite. So `gateChannel` and `revertChannel` start from `guild.channels.fetch(id, { force: true })` (`liveChannel` in `apply.js`); without it a list change (revert then gate at once) planned from the pre-revert state. Test fakes for this must not update the cache on edit/delete. Residual (left as is): `edit()` still merges the bits it does not set from the cached overwrite, so a delayed CHANNEL_UPDATE for an earlier write landing between the forced fetch and the edit could write stale unchanged bits back; the only cache-free writes are `create()` (a full replace, which with flag-name options would drop bits discord.js does not know) or the private `upsert(..., existing)`, both of which would change the write contract every test fake relies on.
- Verification synced children: Discord never changes a channel when its category's overwrites are edited (category sync is a copy made by the client), and discord.js computes `permissionsLocked` from caches. So every channel is gated on its own with its own undo record, synced or not, and the setup preview counts them.
- Verification: a channel created inside a gated category copies the category's gated overwrites, so it looks private. `gateChannel` handles it: when the channel has no record, its parent has one, and its @everyone and Verified overwrites equal the parent's current ones, the parent's recorded original becomes the channel's original (planned and recorded from it), so it is gated by its own kind and `remove` opens it like its category. A child that differs from its category in those two overwrites is judged as it is (a really private one stays untouched).
- Verification `remove` order: it sets state `none` and `enabled: false` first, then cancels the jobs, then restores records, re-listing until only failures are left (at most 5 passes). A gate batch already running checks the state before every channel, and both the gate job and the channel-create event revert a channel they gated if the state became `none` meanwhile. If some channels fail, their records stay and the old state comes back (`rolling_out` becomes `failed`, since its jobs are gone), so remove can be run again. A Verified role that was deleted is treated as already removed (Discord drops its overwrites); only @everyone and the bot are restored.
- Verification leaking-role warning: the setup preview lists gated channels where another role has an explicit View allow (its members keep seeing the channel). It is informational only; nothing is changed for those roles.
- Verification: the Verified role must stay below the bot's top role (`botCanGive`). If it is moved above, button and captcha verifies fail with a "tell a moderator" reply, and a rollout still in the grant step ends `failed`. The same happens if the role gains a staff permission (`isDangerousRole`, checked at every grant: button, captcha, manual verify, bot join and the rollout grant). `/verification status` then shows a warning line, and the first refused grant per guild per hour writes one mod-log line (`role_dangerous`, `createDangerAlert` in `verify.js`, in memory; bot joins log it too although their grant line is silent).
- Verification config has extra JSON keys outside `readConfig`'s defaults (`grantDone`, `failedChannels`, `failedChannelIds` (first 10 failed channel ids, shown by status), `rolloutBy`; `cutoff` is read but set by the rollout). Always merge with `setFeature` (it shallow-merges the config) and never replace the whole config, or a running rollout loses its state.
- Verification captcha is always English (image and messages), whatever the server language. Challenges (code, wrong count, cooldown) live in memory and are lost on restart; the setup Confirm choices (`pending` in `commands.js`) are in memory too, so a restart makes the Confirm button say expired. The captcha mode is chosen at `/verification setup mode:` or later with `/verification mode`.
- Verification: migration 008 (`verification_overwrites`) runs on the next bot start and `/verification` appears after `npm run deploy`. Setup refuses when the bot lacks one of Manage Roles, Manage Channels, View Channel, Send Messages, Embed Links or Attach Files, when @everyone has Administrator, when the chosen role is unusable (@everyone, managed, or not below the bot: `botCanGive`), when the role has staff permissions (`isDangerousRole`, also for a role reused from an earlier setup), when a role the admin picks is not strictly below their highest role (`callerCanGive`, owner exempt; a reused role is not held to this), when the chosen verify channel is hidden from @everyone, when the state is not `none`, and while undo records are left (`remove` sets state `none` before restoring, so records mean a remove is running or was interrupted by a restart: run remove again). Confirm re-checks all of this; a Confirm during a running remove is also refused by the shared in-flight guard.
- Verification: a `failed` rollout cannot be retried by a command (setup needs state `none`); recover with `/verification remove`, then `/verification setup`. While `failed` the gate keeps working where it was applied: verifying works, joining bots get Verified, and, once the grant had finished (`grantDone`), new channels are gated and list changes re-apply at once. Before the grant is done nothing is gated early: a new channel or a list change in `rolling_out` waits for the gate job, and in a `failed` grant nothing is gated.
- Verification unverified policy: needs Kick Members on the bot and `npm run deploy` for the new `unverified` subcommand; no migration. A member at or above the bot's top role, the owner, bots and bot managers are silently spared (no log line). The warn counts as an ordinary warning in `/warnings`, but that command only works while the moderation feature is enabled (the case is recorded and logged either way).
- Verification unverified policy, known fail-safe edges (from the final reviews): if verification is turned off or removed while a warn is being sent, or a write throws after the warn, the member is simply not kicked (possibly with one wrong "kick skipped: the warning never ran" mod-log line). A guild missing from the client cache makes the job disappear (`load` returns null and the scheduler drops it), and so does a job that comes due while the feature is disabled (or state none, or policy none): it is dropped, not kept for later. All of these fail toward not kicking. The one edge that could kick wrongly, a member who left and rejoined unseen (bot down, or rejoin while verification was off, after a mid-warn leave re-inserted the kick row), is closed by `joinedAt` in the payload: at fire time a member whose `joinedTimestamp` differs is left alone. Jobs queued before that field existed have no `joinedAt` and skip the check.
- Verification unverified policy: a partial `/verification remove` (some channels could not be restored, state put back so remove can be retried) has already cancelled every queued warn and kick job. The members queued at that point are never warned or kicked; only later joins are queued again.
- Verification unverified policy: queued jobs are never rewritten by a policy change, so after switching `kick` to `warn_kick` (or changing times) old members keep the old schedule and only joins after the change use the new one. Members who joined before the policy was set, or while verification was not running, are never queued.
- Anti-raid: needs Kick Members (it kicks the young accounts) and Manage Server (Discord's own invite pause, `PUT /guilds/{id}/incident-actions`; Discord caps the pause at 24 hours) on the bot, plus the Server Members intent, and `npm run deploy` for `/antiraid`. There is no migration: the settings and the lockdown state live in the `antiraid` feature config. The join counter is in memory only, so it is empty after a bot restart and `/antiraid start` right after a restart removes nobody.
- Anti-raid: the ping role is never the guild id and never `@everyone` (`/antiraid config ping_role:` refuses it, and the manager role fallback refuses it too, since @everyone shares the guild id). The alert is one mod-log line plus a second message that pings exactly one role; with the logging feature off there is no mod-log channel, so the alert is skipped (`alertResult` `no_channel`) and the lockdown still runs.
- Anti-raid: `invitesPausedByUs` decides whose pause is lifted. A pause that was already there (Discord's own raid protection, or an admin's) is left alone, and the end of the lockdown does not lift it. Only a pause this lockdown made is lifted, and only then the invites open again.
- Anti-raid: `/antiraid disable` ends a running lockdown first, otherwise the feature would be off while the lockdown was still on. The end of a lockdown clears the join list, so the same burst cannot start a second lockdown right after it.
- Anti-raid: the join window and the join threshold have hard limits (`joins` 3-100, `window` 10 s-10 m, `account_age` 1 h-90 d, `duration` 5 m-24 h). A stored value outside its range reads back as the default, so a hand-edited config cannot break the detector; `/antiraid config` refuses such a value and saves nothing.
