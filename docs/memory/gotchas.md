# Gotchas

- `stickyroles` is still a "coming soon" stub in `core/registry.js`, but `/autorole reassign` and `/autorole blacklist` already do it. Remove the stub or point it at `/autorole`.
- The bot's highest role must sit above any role it gives, or Discord refuses (autorole).
- Privileged intents needed: Server Members and Message Content. Guilds, Guild Messages, Guild Expressions, Guild Moderation and Guild Voice States are not privileged.
- Invite permissions: View Channels, Send Messages, Read Message History, Embed Links, Attach Files, Manage Roles, Kick Members, Ban Members, Moderate Members (the last three came with moderation). Update the README invite list as phases add Manage Messages/Channels/Nicknames. The `GuildMessageReactions` intent is still not added (reaction roles, starboard need it).
- `DEV_GUILD_ID` set means commands register to that one server only and update instantly; unset means global (slow to propagate).
- Setting a feature's config merges into existing jsonb (`setFeature`), it does not replace it.
- `graphify-out/` can be stale; compare its commit with `git rev-parse HEAD`.
- Logging config shape (in the `logging` feature row): `channels{category:id}`, `disabledEvents[]` (everything is on once a channel resolves), `ignore{channels[],members[],prefixes[]}`. `setFeature` shallow-merges top-level keys, so always write the whole nested object (`channels`, `ignore`), never a partial one.
- Logging channel lookup: `channels[category]`, else for the `join` category `channels.members` (old join/leave logs keep working), else `channels.default`, else nothing.
- Logging ignore lists only affect message events (delete, edit, purge, invite posted). Events inside a log channel are never logged (loop guard).
- Logging "By" needs View Audit Log; it is optional and the invite list does not require it. `/logging setup` needs Manage Channels and is not idempotent: a second run adds a new "Logs" category.
- Logging "By" lookups are lazy: handlers pass `opts.executor` (an async function) to `sendLog`, which calls it only after the enabled, event, ignore, channel and loop-guard checks pass. Timeout attribution filters audit entries on the `communication_disabled_until` change; ban handlers use `ban.user` without fetching (gateway bans are always partial). Channel create/delete/update do not use the loop guard, so changes to log channels are themselves logged.
- Moderation cases are logged to the `mod` logging category through the hidden `modAction` event. If logging is off or no `mod` channel resolves, `sendLog` returns `null`: the action still succeeds but the case has no stored log message (so `/reason` cannot edit one). See [[roadmap]].
- Setup and testing docs: `docs/discord-bot-setup.md` (developer portal, intents, invite, `.env`, troubleshooting) and `docs/testing-checklist.md` (tick-box manual test per feature). When a feature or invite permission changes, update both and the README manual check. `/help` needs no edit for new subcommands: it reads the command definitions.
- Repo hosting: `origin` is the private GitHub repo `Haruru0-0/jalter` (branches `autorole-upgrade`, `phase-1`). Commits use the global git identity (Haru); no Co-Authored-By trailers. History was rewritten once on 2026-10-14 before the first stable push; local tags `backup-before-rewrite-*` hold the old history and can be deleted.
- Scheduler handlers must be idempotent (at-least-once: a crash or expired claim can run a job twice) and must return, not throw, on permanent Discord errors (HTTP 4xx other than 429, unknown member or role, missing permission); throwing means retry, and after 5 attempts the job is dropped. A feature adds a job type by exporting `jobs` from its module; `collectModules` throws on duplicate types. A job type nobody registered just sits in `scheduled_jobs` (see [[architecture]], [[decisions]]).
- Timed roles no longer have a `pending_roles` table: they are `scheduled_jobs` rows of type `autorole.grant` with key `userId:roleId` and payload `{userId, roleId}`.
- `/logging event` already has 25 choices (the Discord limit), so the mod log uses a hidden `modAction` event outside `EVENTS` (`HIDDEN_EVENTS`, `categoryOf`).
- GitLab mirror: `scripts/mirror-to-gitlab.sh` adds `.github/workflows/mirror-to-gitlab.yml` to each local repo (default list: jalter, Nebula, PortaGen, aesthetic-portfolio-os, notioncraft-ai, steam-games-analysis; not career-ops) and sets the `GITLAB_TOKEN` secret. Mirrors GitHub to `gitlab.com/Haruru0-0/<repo>` on every push and nightly; GitLab copies are read-only (overwritten). New repo: run the script with its name. The script reads the token from `$GITLAB_TOKEN`, then the Windows credential vault (saved on request after the first prompt; `--forget` deletes it), then prompts. Status: ran for jalter and Nebula; PortaGen, aesthetic-portfolio-os, notioncraft-ai and steam-games-analysis still need a rerun. PortaGen history was scrubbed of a leaked Supabase DB password by another session (rotate the password).
- Moderation: the DM to the target goes out before the Discord action for every punishment (warn, timeout, mute, kick, ban), so a refused action can still have sent a DM. `/unban`, `/untimeout`, `/unmute` send none.
- Moderation: the "already muted" check decides by the latest `mute`/`unmute` case of the user (`isCurrentlyMuted`). `expireMute` skips only when that latest case is a mute that is still running (permanent, or ending more than 1 s from now), so a newer mute keeps the role. Otherwise it fetches the member and does nothing if they left or no longer have the mute role; if they still have it, it removes it and writes the bot's "expired" unmute case. So a timed mute whose case failed to save still expires, and a rerun never logs a second case. A manual `/unmute` or `/unban`, and a new permanent mute or ban, cancel the older expiry job.
- Moderation: the action commands treat only Discord error 10007 (Unknown Member) from the member lookup as "not in the server"; any other lookup error is rethrown (the router answers `common.error`), so hierarchy checks are never skipped by a failed lookup. A missing permission replies `moderation.err.not_allowed`.
- Moderation: durations are at least 1 minute and at most 10 years (315 360 000 s) for any action, 28 days for a timeout (`checkDuration`, `too_long`); the `duration` option is at most 32 characters. The cap keeps `ends_at` storable, since the Discord action runs before the case is saved.
- Moderation: `/reason` updates the case, then edits the stored mod log message best effort (a deleted message or channel is ignored). `/warnings edit` changes the reason only in the database.
- Moderation: `mod.unban` and `mod.unmute` handlers run whether or not the feature is enabled; the rejoin mute (`reapplyMute`) needs the feature on and a mute role that still exists. `kick`, `timeout`, `untimeout`, `mute`, `unmute` need the user to be in the server; `warn`, `ban`, `unban` work by user ID.
- Moderation: new commands only appear after `npm run deploy`, and migration 006 (`mod_cases`, `mod_counters`) runs on the next bot start.
- Auto-created channels (`src/core/auto-channel.js`, needs Manage Channels): logging makes `<category>-logs` (or `logs`) in a private "Logs" category (id kept in `config.categoryId`) when an event has no category or default channel; greet/leave/boost make `welcome`/`goodbye`/`boosts` when a message is saved or a member event fires with the kind on and no `channelId`. A chosen channel is never replaced, and a configured channel that was deleted is not recreated (logs drop with a warning, greet gives `no-channel`). Creation is one run at a time per guild and category/kind (`singleFlight`); failure only warns. See [[features-built]].
