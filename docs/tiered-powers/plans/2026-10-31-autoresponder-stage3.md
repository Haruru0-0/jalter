# Autoresponder Stage 3 (Buttons) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use tiered-powers:subagent-driven-development (recommended) or tiered-powers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Autoresponder replies can carry buttons. Each stored button runs its own script when pressed, with `invoker_only` and `limited`/`strict` press rules, state that survives a restart, `/autoresponder button add|edit|remove|list`, and builder controls.

**Architecture:** Two new tables (stored buttons per server; one record per posted message with its buttons, the original words and random results, and press state). `{addbutton:name}` / `{addlinkbutton:...}` are compiled like `embed:name` and attach components when the reply is sent; the send path now returns the sent message and stores the record. A press is a new component kind (`autoresponder:p:<messageId>:<index>`) handled by a press runner extracted from the message handler: it checks record, rule, button and press rules, claims the press atomically, then runs the button script with the presser as "the member" through the existing `prepareRun` / `evaluate` / `executePlan`.

**Tech Stack:** Node 22 ESM, discord.js 14.27, Postgres, `node --test`.

**Spec:** `docs/tiered-powers/specs/2026-10-31-autoresponder-stage3-design.md` (its "calls made after the builder check" are binding). Parent: `2026-10-24-autoresponder-design.md`; stage 2: `2026-10-24-autoresponder-stage2-design.md`; builder: `2026-10-24-autoresponder-builder-design.md`.

## Global Constraints

- Node 22+, ESM, discord.js 14.27.0, no new dependency, no new intent. Migration `011_autoresponder_buttons.sql` (next after 010); every new table is added to the `TRUNCATE` list in `resetDb` (`src/db/index.js`); posted-message records reference `autoresponder_rules(id)` with `ON DELETE CASCADE`.
- Every user-facing string in `src/i18n/en.json`, `fr.json`, `ar.json` (real translations; `test/i18n.test.js`). New compile codes join `COMPILE_ERROR_CODES` with `autoresponder.error.<CODE>`; new run-time codes join `RUN_ERROR_CODES` with `autoresponder.run.<CODE>`; the loop tests in `autoresponder-commands.test.js` enforce both.
- A stored button: unique per server by `name` (`^[a-z0-9_-]{1,16}$`, like embed names), `label` (1 to 80), optional `emoji`, `style` one of `blue`, `green`, `grey`, `red` (ButtonStyle Primary, Success, Secondary, Danger), `script` (up to 4000, compiled and stored), `invoker_only` (default false), `limitations` one of `none`, `limited`, `strict` (default `none`). At most 50 stored buttons per server (my call, like the 100-rule cap).
- Attaching: `{addbutton:name}` (name must exist at save: `BUTTON_NOT_FOUND`) and `{addlinkbutton:label|url}` / `{addlinkbutton:label|url|emoji}` (`http`/`https` URL up to 512, label up to 80: `LINK_URL_INVALID`); at most 25 per reply counted statically (`TOO_MANY_BUTTONS`), in script order, 5 per row; `{dm}` with any button is `BUTTONS_NEED_CHANNEL`; a reply with buttons but no text and no embed is `BUTTONS_NEED_TEXT`; with `{sendto:#channel}` the record uses the sent message's channel. Custom id `autoresponder:p:<messageId>:<index>` (at most 100 characters).
- Record: message id and channel, guild, rule id, invoker id (the member the script ran for: the triggering member, or the presser for a chained reply), the buttons attached, the original words (the trigger remainder) and the random results, press state, `expires_at` 14 days after posting; a housekeeping function deletes expired rows. Chained replies copy the words and random results forward.
- A press, in order: feature on; record exists and not expired; the rule exists and is **enabled**; the stored button exists; `invoker_only` (presser must be the invoker); a 3-second per presser per message floor in memory; the `limited`/`strict` claim (one atomic statement: a `none` press changes nothing, `limited` marks that button, `strict` locks the whole message and refuses every later press); then the button script's own gates (rule-level conditions and the rule cooldown are NOT used; `{cooldown}` in the button script is per presser per button, stored in the database). `deferUpdate` first; the reply is a normal public channel reply to the button's message (`failIfNotExists: false`, no ping of the replied user, falling back to a channel send); disabling is an edit of the original message; refusals are ephemeral interaction replies.
- Button scripts: the presser is "the member" for placeholders, role changes and nicknames (`isDangerousRole`, `botCanGive` and the stage 2 target checks apply); restored words are re-checked at press time (`requirearg`, checked users, role targets); `allowedUsers` is computed fresh from the button script and those re-checked words; random tokens resolve against the button's own `range`/`choose` functions and, for a kind the button does not define, from the random results stored with the message (such tokens are always live in button scripts); `{delete}` and `{react}` act on the message that carries the button; `{reactreply}` and `{delete_reply}` act on the posted reply; `{addbutton}`/`{addlinkbutton}` are allowed in button scripts; a missing stored button at send time is skipped with run error `BUTTON_MISSING`; a press on a removed button answers "expired".
- Rules compiled before this stage need no recompile and no migration of stored rules; a rule with no buttons costs nothing extra per message.
- Tests hit the DB (`npm test`, concurrency 1; one test process at a time). Commit style `feat(autoresponder): ...`, the user's own git name and email, no Co-Authored-By Claude trailer. Never stage `docs/memory/roadmap.md`, `docs/memory/.obsidian/workspace.json` or `test/features/automod-*.test.js` (the user's uncommitted edits).

## Review Focus

1. Press races and permissions: two presses at the same moment on a `limited`/`strict` button claim once; a non-invoker on an `invoker_only` button is refused; after a `strict` press every button is refused; a non-manager member can press (the manager guard is not used for presses) (Tasks 1, 3).
2. A press on anything gone does nothing else: expired record, deleted or disabled rule, removed stored button, feature switched off, message from another server (Task 3).
3. Safety at press time: pings come only from the button script and re-checked user words; role changes use the presser with the usual role checks; a removed or left target is skipped with the rest still running (Task 3).
4. Save-time refusals: `{addbutton}` with `{dm}`, no text, an unknown name, a 26th button, a bad link URL (Task 2).
5. Limits and growth: custom ids at most 100, 5 per row, 25 per message, records expire and are cleaned up, a rule with no buttons adds no database work (Tasks 1, 3).
