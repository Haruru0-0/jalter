# Anti-raid Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use tiered-powers:subagent-driven-development (recommended) or tiered-powers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A join-rate detector that starts a lockdown on a burst of human joins: alert the mods with a role ping, pause invites, kick the young accounts in the burst, and end by timer or command.

**Architecture:** A new feature `src/features/antiraid/`: config and commands (Task 1), an in-memory join store (Task 2), a lockdown engine with an `antiraid.end` scheduler job (Task 3), then the `GuildMemberAdd` detector and the `start`/`end` commands wired to the engine (Task 4). Kicks go through the moderation engine `runAction`; state lives in the feature config and the shared scheduler, so no migration is needed.

**Tech Stack:** Node 22+ ESM, discord.js 14.27 (`Guild#setIncidentActions`), Postgres, `node:test`, the shared scheduler (`src/core/scheduler.js`), moderation `runAction`.

**Spec:** `docs/tiered-powers/specs/2026-10-19-antiraid-design.md` (the reuse list and the settled calls in its Constraints section are binding).

## Global Constraints
- Feature key `antiraid`, folder `src/features/antiraid/`, off by default, registered as `f('antiraid', 2, 'antiraid', { enableCommand: 'antiraid enable' })` in `src/core/registry.js`; listed in `src/modules.js`. All commands under `/antiraid`, guarded with `guard(interaction, ctx, 'antiraid', { requireEnabled: false })` (manager); replies ephemeral. `stickyroles` stays a "Coming soon" stub.
- Config (`guild_settings` feature `antiraid`, JSON, always merge-written with `setFeature`, never replaced). Defaults and ranges: `joins` 10 (3 to 100); `windowSeconds` 60 (10 to 600); `accountAgeSeconds` 604800 (3600 to 7776000, i.e. 1 hour to 90 days); `durationSeconds` 1800 (300 to 86400); `pingRoleId` null (never `@everyone`, never the guild id). State keys: `state` (`'idle'|'locked'`, default `'idle'`), `lockedAt`, `lockedUntil` (epoch ms or null), `startedBy` (user id, `'auto'`, or null), `kicked` (count), `invitesPausedByUs` (boolean), `inviteResult` (`'none'|'paused'|'already'|'failed'`), `alertResult` (`'none'|'sent'|'no_channel'|'failed'`).
- Times are parsed with `parseDuration` and shown with `formatDuration` (`src/core/duration.js`).
- Job type `antiraid.end`, key `'lockdown'`, registered through the module's `jobs` export. Only humans are counted; bots are never counted or kicked.
- Only humans who joined inside the detection window and whose Discord account is younger than `accountAgeSeconds` are kicked; the owner, a member whose highest role is at or above the bot's highest role, and anyone for whom `canManage` is true are never kicked (the unverified-policy rules `isSpared`, `fetchMember` in `src/features/verification/unverified-jobs.js`). A verified member is not spared. At most 100 kicks per lockdown start.
- Kicks are made only with `runAction(ctx, { guild, actor: guild.members.me, type: 'kick', targetId, target, reason, config, lang })` where `config` is `readModConfig((await getFeature(ctx.db, guildId, 'moderation')).config)`; the moderation feature need not be enabled. Reason text comes from `antiraid.kick_reason` in the server language.
- Invite pause: `guild.setIncidentActions({ invitesDisabledUntil: new Date(lockedUntil) })`; lift with `invitesDisabledUntil: null`, only when the lockdown made the pause (`invitesPausedByUs`). If `guild.incidentsData?.invitesDisabledUntil` is already in the future, leave it alone (`inviteResult: 'already'`). A refused pause is `inviteResult: 'failed'`; the lockdown still runs.
- Alert: the mod-log message is sent with `sendLog(ctx, guildId, 'modAction', embed)` (it finds or creates the channel); when it returns a channel id and a ping role is known (`pingRoleId`, else the panel `managerRoleId`, never the guild id), a second short message with the ping is sent to that channel with `trySend(channel, { content, allowedMentions: safeMentions([roleId]) })`. `sendLog` returning null means `alertResult: 'no_channel'`; the lockdown still runs.
- A lockdown start flips the state with one conditional SQL update (`state` not already `'locked'`, feature enabled) so two starts can never both win. Ending is the same kind of conditional update and is idempotent.
- i18n: every user-facing string in `src/i18n/en.json`, `fr.json`, `ar.json` (flat dotted keys under `antiraid.`, real translations, `{name}` placeholders); parity is enforced by `test/i18n.test.js`.
- Tests: `node --test --test-concurrency=1 test/features/<file>`; full run `npm test` (needs Postgres: `docker compose up -d`; never run two test processes at once). Fakes are inline in each test file; the DB comes from `testDb()` in `test/helpers/db.js`.
- Commits stage explicit files only; never stage `docs/memory/.obsidian/workspace.json`, README.md or `test/features/automod-*.test.js` (unrelated user edits); no `Co-Authored-By` trailer.

## Review Focus
- Only the intended accounts are kicked: an older account, a bot, the owner, a member at or above the bot, and a manager are never kicked, and the cap of 100 holds.
- A lockdown always ends: by timer (also after a restart: state in config plus the queued job), by `end`, and by `disable`; the invite pause is lifted only when the lockdown made it, and an end job for a lockdown that already ended does nothing.
- One burst starts one lockdown: concurrent triggers, a trigger while locked, and a burst re-triggering right after the end (the join list is cleared at the end) all start nothing new.
- A partial failure is visible and harmless: a refused invite pause, no mod-log channel, a refused or failed kick, and a thrown Discord error never stop the rest of the lockdown and show up in the alert or `/antiraid status`.
- Nothing happens while the feature is off or state is idle: joins are not counted, a young join is not kicked, and a manual `end` when idle is refused with a clear reply.

### Task 3: The lockdown engine

**Files:**
- Create: `src/features/antiraid/lockdown.js`
- Modify: `src/features/antiraid/index.js` (export `jobs`), `src/i18n/*.json` (`antiraid.alert.*`, `antiraid.kick_reason`, `antiraid.log.*`)
- Test: `test/features/antiraid-lockdown.test.js`

**Tier:** opus - kicks real members, a conditional state machine, Discord incident actions, the scheduler and partial failure all meet here.

**Interfaces:**
- Consumes: Task 1 `readConfig`; Task 2 `joins` (to clear at the end); `scheduleJob`/`cancelJobs`; `runAction`, moderation `readConfig as readModConfig`; `isSpared`, `fetchMember` (exported in Task 1); `sendLog`, `trySend`, `fetchSendable`, `safeMentions`; `getFeature`/`setFeature`; `getLang`, `t`, `formatDuration`.
- Produces in `lockdown.js`: `END_JOB = 'antiraid.end'`, `END_KEY = 'lockdown'`;
  - `startLockdown(ctx, guild, { trigger: 'auto' | 'manual', startedBy: string | null, joinedCount: number, candidates: Array<{ userId: string, createdAt: number }> }, deps?): Promise<{ ok: true, kicked: number } | { ok: false, reason: 'already_locked' | 'disabled' }>` - order: conditional state flip (sets `state: 'locked'`, `lockedAt`, `lockedUntil = now + durationSeconds*1000`, `startedBy`, `kicked: 0`, reset the two result keys); queue the `antiraid.end` job at `lockedUntil`; send the alert (numbers: joins counted and window, candidates and the age limit, end time, trigger and who) and the ping message; pause invites; then kick the candidates sequentially (up to 100) whose account age is below `accountAgeSeconds`; finally save `kicked`, `inviteResult`, `alertResult` (merge-write). Every step is wrapped so a throw or refusal records its result and the next step still runs.
  - `endLockdown(ctx, guild, { by: 'timer' | 'manual' | 'disable', actorId?: string | null }, deps?): Promise<{ ok: true } | { ok: false, reason: 'not_locked' }>` - conditional flip back to idle (`rowCount` decides), cancel the end job, lift the invite pause only when `invitesPausedByUs`, `joins.clear(guild.id)`, write one mod-log line through `sendLog` (who or what ended it, accounts removed, whether the pause was lifted).
  - `kickYoungJoin(ctx, guild, member, deps?): Promise<'kicked' | 'spared' | 'old' | 'failed'>` - for a human who joins while locked: `'old'` when the account is not younger than `accountAgeSeconds` (nothing done), otherwise the same fetch, spared check and `runAction` kick as the burst kick and `kicked` count incremented (atomic `jsonb` increment or read-merge-write).
  - `endJob(ctx, job, deps?)` and `export const jobs = { [END_JOB]: endJob }`: guild missing from the cache returns quietly; otherwise `endLockdown(... { by: 'timer' })`; a throw is rethrown for retry; on the final attempt (`job.attempts >= 5`, scheduler `MAX_ATTEMPTS`) conclude as ended anyway (state idle) so a lockdown can never stay stuck.
  - `deps = { runAction, sendLog, trySend, now, joins }` for tests.
- Kick candidates are filtered by `account age < accountAgeSeconds` using `Date.now() - createdAt`; a candidate who left, is a bot, is spared or whose kick is refused is skipped (a `not_in_server` refusal is silent; any other refusal only lowers the kicked count; no per-member log line).

### Task 4: Detector, `start` and `end` commands, and `disable`

- Test: `test/features/antiraid-events.test.js`, `test/features/antiraid-commands.test.js`

**Tier:** sonnet - wires finished pieces; the detector has several state cases.

**Interfaces:**
- Consumes: Tasks 1-3 (`readConfig`, `joins`, `startLockdown`, `endLockdown`, `kickYoungJoin`).
- Produces: `createEvents(deps = {})` and `export const events = createEvents()` with one entry `{ name: Events.GuildMemberAdd, execute }` wrapped with `safe` (never throws): for a human member in a guild where the feature is enabled: when `state === 'locked'` call `kickYoungJoin` and do not count the join; otherwise `count = joins.record(guildId, { userId, createdAt: member.user.createdTimestamp }, now, windowSeconds * 1000)` and when `count >= cfg.joins` call `startLockdown(ctx, guild, { trigger: 'auto', startedBy: 'auto', joinedCount: count, candidates: joins.recent(...) })`. Bots, a disabled feature and non-guild members do nothing (and are not counted). Starts the sweep (`startAntiraidSweep`) lazily on the first handled join.
- `/antiraid start`: refuses when `state` is locked; otherwise `startLockdown` with `trigger: 'manual'`, `startedBy: interaction.user.id`, `joinedCount` = recent count, candidates from `joins.recent`; replies with the result (accounts removed, end time, invite pause and alert results). `/antiraid end`: refused with a clear reply when idle; otherwise `endLockdown({ by: 'manual', actorId })`. `/antiraid disable`: when locked, calls `endLockdown({ by: 'disable' })` first, then the normal toggle.
